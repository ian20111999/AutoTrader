# 2026-10-01 測試網下單＋風控（ROADMAP 第 6 步）執行計畫

## 前置狀態

ROADMAP 1-5 全部完成（回測引擎、桌面 App、Binance 唯讀連線、模擬交易）。使用者已同意跨過「第一次出現送單程式碼」這條安全線，但僅限**測試網**；正式環境下單是第 7 步，需要另一次明確同意。

## 核心架構轉折（跟前面所有步驟不同之處）

PaperEngine（5.1）是「同步、確定性」的：給定目標部位，立刻算出成交價、立刻更新帳本。真實下單不是這樣——送出訂單後要等交易所回報（NEW/FILLED/PARTIALLY_FILLED/REJECTED/CANCELED），可能部分成交、可能被拒絕。這一步不能把 PaperEngine 的「假設立刻成交」邏輯直接套在真實下單上，需要新的「送出去、等回報、更新帳本」流程。

## 範圍

只做**測試網**（testnet.binance.vision），不管正式環境下單端點。只做現貨市價單（最簡單、不用處理掛單簿），限價單/合約下單之後需要時再做。

## 子步驟

- [ ] 6.1 Testnet 金鑰獨立存放：Keychain 新增一組 testnet 專用 service name，跟 4.1 正式環境唯讀金鑰分開
- [ ] 6.2 Testnet REST client＋下單簽名：`at-binance` 的 `base_url` 可指向 testnet，新增簽名過的 POST 下單（市價單）＋查詢訂單狀態＋撤單。先用官方文件範例離線驗證簽名，不連真實網路
- [ ] 6.3 風控層：每日虧損上限、一鍵停止、單筆下單金額上限——下單前的檢查閘門，邏輯本身不連網路，可注入假狀態測試
- [ ] 6.4 把策略執行接上測試網下單：仿 5.x 的架構，但 `on_bar` 後透過 6.2/6.3 真的送單、等回報、更新帳本，不是模擬成交
- [ ] 6.5 桌面 App「測試網交易」頁面＋風控設定（一鍵停止要明顯）
- [ ] 6.6 真實測試網端到端驗證（需要使用者提供的測試網金鑰）

## 安全規則（不可違反，比照前面各節）

- 只能連 `testnet.binance.vision`，不可以連 `api.binance.com` 的下單端點（唯讀端點如 4.x 已驗證過的可以繼續用正式環境）。
- 風控層（每日虧損上限、一鍵停止）在 6.4 真正送單之前必須先做出來、先驗證，不能先送單再補風控。
- 這一步做完前，第 7 步（正式環境真錢）維持完全不可碰。

## 驗證方式與模型分配

延續既有模式：Claude 投資部（opus）做核心邏輯 → Claude QA 獨立驗證 → **這一步額外加一輪 Codex 獨立審查**（6.2 下單簽名、6.3 風控閘門、6.4 下單/回報整合這幾個最高風險的子步驟），作為跟 Claude 同系列模型不同的第二意見。較機械的子步驟（6.1 金鑰存放複用 4.1 架構）維持單一 Claude 驗證即可，不需要 Codex，控制 token 消耗。
