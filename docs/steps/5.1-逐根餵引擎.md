# 5.1 逐根餵：讓回測與模擬交易共用同一顆引擎

## 做了什麼

把 `crates/core/src/backtest.rs` 裡 `run_backtest` 的**內部迴圈**抽成一個會自己記住
帳本狀態、一次只吃一根 K 線的引擎 `PaperEngine`；`run_backtest` 本身變成「建立引擎 →
把整段歷史 K 線逐根餵進去 → 把回傳的權益點收成一條曲線」的薄殼。

只動了一個檔案，公開 API **只新增、沒有刪改**（`BacktestConfig`／`BacktestResult`／
`EquityPoint`／`BacktestError` 的欄位與語意完全沒變，所以 `app/src-tauri` 的 Tauri
command 與 `metrics.rs` 一個字都不用改）。

新的介面：

| 方法 | 做什麼 |
|---|---|
| `PaperEngine::new(&BacktestConfig) -> Result<PaperEngine, BacktestError>` | 建立引擎，順便把原本 `run_backtest` 開頭那些一次性驗證（起始資金、滑價、吃單費率、資金費率、維持保證金率）跑完 |
| `PaperEngine::on_bar(&mut self, &Bar, &mut dyn Strategy) -> Result<EquityPoint, BacktestError>` | 餵進**一根已收盤**的 K 線，回傳這根收盤時的權益點 |
| `PaperEngine::cash() -> Fixed` | 現金餘額（負數＝跟交易所借的錢） |
| `PaperEngine::position() -> Fixed` | 帶正負號的持倉數量（正做多、負做空） |
| `PaperEngine::trades() -> usize` | 累計成交筆數（含強制平倉） |
| `PaperEngine::liquidations() -> usize` | 累計爆倉次數 |

`run_backtest` 現在長這樣，整個函式就這幾行：

```rust
let mut engine = PaperEngine::new(config)?;
let mut curve = Vec::with_capacity(bars.len());
for bar in bars {
    curve.push(engine.on_bar(bar, strategy)?);
}
Ok(BacktestResult { curve, trades: engine.trades(), liquidations: engine.liquidations() })
```

`on_bar` 裡面五個步驟的順序和原本迴圈一字不差：
① 收付資金費 → ② 檢查強制平倉（開盤價）→ ③ 成交上一根留下的目標（用這根開盤價）→
④ 用這根收盤價評價、記一點權益 → ⑤ 問策略這根收盤想要什麼部位（留到下一根成交）。

## 為什麼要這樣改

**即時行情不會給你一個陣列。** 模擬交易（5.2）的 K 線是 WebSocket 一根一根送來的，
使用者按停止才結束，永遠等不到「集滿一整段」。原本的 `run_backtest` 只吃 `&[Bar]`，
模擬交易要嘛等資料湊滿（等於不是即時），要嘛自己再寫一套成交模擬——**後者才是真正的
危險**：兩套模擬邏輯遲早會分岔，到時候回測說賺錢、模擬盤說虧錢，你不知道該信哪一個。

現在財務邏輯只有一份，回測和模擬交易跑的是同一段程式，數字不可能分岔。

## 逐根餵和索引版差在哪：三個「往前看」要換成狀態

一次吃整個陣列時可以用 `bars[index - 1]` 往前看，逐根餵不行。原本依賴索引的地方剛好三個：

| 原本 | 現在 | 為什麼要小心 |
|---|---|---|
| `bar.open_time <= bars[index - 1].open_time` 時間單調性檢查 | `prev_open_time: Option<i64>` | 時間倒退會把資金費反過來收，等於憑空生錢 |
| `funding_periods(bars[index - 1].open_time, bar.open_time)` | 同一個 `prev_open_time` | 記錯的話資金費會少收或多收，而且**權益曲線看起來還很正常**，最難發現 |
| 錯誤裡的 `index`（例如 `Overflow { index }`） | `bars_seen: usize`（已經餵完幾根） | 數錯會讓錯誤訊息指到錯的那根 K 線 |

還有一個對應關係要對上：原本「**第一根**永遠不成交、`pending` 是 `None`、不收資金費」
這個特例，在逐根餵的世界裡就是「引擎剛建立、還沒呼叫過 `on_bar`」這個初始狀態——
也就是 `prev_open_time == None`。兩者完全等價，所以第一根 K 線的開盤價照舊不檢查
（用不到它，不會拿它算出錯誤的成交）。

**刻意沒做的事：引擎沒有 `reset()`。** 要重跑就 `PaperEngine::new` 一個新的。
多一個 `reset()` 就多一個「重跑第二次忘記清某個欄位」的出錯機會，而它一點也不省事。

## 這一步最大的風險，以及怎麼把它拆掉

`backtest.rs` 是 2.2-2.5 累積五輪驗證、2.8 又用獨立實作對照過的程式。重構它的風險不是
「編不過」，是**悄悄改變某個數字而測試剛好沒抓到**。所以驗證分三層做，一層比一層嚴：

**第一層：既有測試逐項對照。** 重構前先把整個 workspace 的測試輸出存檔，重構後再存一次
逐行 diff。結果：唯一的差異是新增的 6 個測試名稱和 `195 passed → 201 passed`，
**45 個 backtest 測試、195 個既有測試沒有任何一項改變**（含 2.3／2.4 的手算迴歸基準、
爆倉、資金費、突變測試）。

**第二層：兩種呼叫方式必須算出同一組數字。** 新增 4 個測試，同一份資料分別用
`run_backtest` 跑完整段、和手動迴圈呼叫 `on_bar` 餵同一段，比對整個 `BacktestResult`
（曲線的時間戳與權益、成交筆數、爆倉次數）：

| 測試 | 情境 | 對照數字 |
|---|---|---|
| `feeding_bar_by_bar_matches_run_backtest_on_a_costed_round_trip` | 吃單 0.1% + 滑價 0.05% 的一趟來回 | `[10015.005, 10000, 9985.005, 9985.005]`、2 筆成交、0 次爆倉 |
| `feeding_bar_by_bar_matches_run_backtest_through_a_liquidation` | 5 倍做多被強制平倉 | `[10000, 200, 200]`、3 筆成交、1 次爆倉 |
| `feeding_bar_by_bar_matches_run_backtest_for_a_short_paying_funding` | 做空 + 8 小時資金費（專門盯 `prev_open_time`） | `[10000, 10000, 10001]` |
| `feeding_bar_by_bar_reports_the_same_error_and_index` | 時間倒退、開盤價 0、數量溢位 | 錯誤種類與 `index` 都相同 |

**第三層：和重構前的實作跑隨機情境差分。** 前兩層都只驗「已經想到的情況」。所以另外
（臨時、驗完就刪）把重構前的迴圈原封不動抄回測試裡當對照組，用固定種子的 xorshift
產生 4000 組隨機情境——隨機的起始資金／費率／滑價／資金費率／維持保證金率、
隨機漫步的價格（含 ±30% 跳空、偶爾插入 0 價格與時間倒退）、隨機的目標部位腳本
（含 −5 到 100 倍槓桿）——比對兩邊的完整結果：

```text
對照驗證 4000 組：成功 1851 組（其中有成交 1303 組、有爆倉 498 組）、回錯誤 2149 組，全部一致
錯誤種類分布：NegativeEquity×301、NonMonotonicTime×586、NonPositivePrice×1190、Overflow×72
```

四種執行期錯誤全部走到過，連錯誤的 `index` 都一致。這一層是真正回答「重構有沒有悄悄
改變行為」的證據：前兩層只能證明我想到的情況沒壞，這一層證明我沒想到的也沒壞。

（這份對照程式沒有留在倉庫裡：它是重構當下的一次性工具，留著就變成一份必須跟著
主程式一起維護的死程式。要重現的話從 `git show` 把舊實作抄回測試模組即可。）

## 怎麼驗證

```bash
# 1. 三道關卡
cargo fmt --all
cargo clippy --all-targets -- -D warnings
cargo test

# 2. 只看回測模組（應該是 51 passed：45 個原有的 + 6 個新的）
cargo test -p at-core backtest:: -- --nocapture

# 3. 只看這一步新增的逐根餵測試
cargo test -p at-core backtest::tests::feeding -- --nocapture
cargo test -p at-core backtest::tests::engine -- --nocapture
```

`cargo test` 的預期結果：`at-core` **201 passed**（重構前是 195，差的 6 個就是這一步
新增的），其餘 crate 的數字全部不變。

## 建議閱讀順序

1. `crates/core/src/backtest.rs` 開頭的模組說明，新增的「逐根餵」那一節（為什麼要有這顆引擎）。
2. 同檔 `PaperEngine` 的型別說明與各欄位註解（狀態有哪些、`prev_open_time` 為什麼要存）。
3. `PaperEngine::on_bar`：五個步驟的順序，和 2.3-2.5 的說明文件對著看。
4. `run_backtest`：確認它真的只剩「逐根呼叫 + 收集」，沒有第二份財務邏輯。
5. 測試裡的 `feed_one_by_one` 輔助函式——5.2 接 WebSocket 時要做的事就是它。

## 動手試試看

1. 把 `on_bar` 最後的 `self.prev_open_time = Some(bar.open_time);` 註解掉，跑
   `cargo test -p at-core backtest::`。`feeding_bar_by_bar_matches_run_backtest_for_a_short_paying_funding`
   會失敗——資金費算不出間隔了（而其他大部分測試還是綠的，這就是為什麼那條測試要存在）。
2. 把 `let index = self.bars_seen;` 改成 `let index = 0;`，跑同一組測試。
   `feeding_bar_by_bar_reports_the_same_error_and_index` 會失敗，錯誤指到錯的 K 線。
3. 在 `engine_state_can_be_read_between_bars` 裡多印幾行
   `engine.cash()` / `engine.position()`，看部位是怎麼一根一根變出來的——這是回測
   看不到、模擬交易畫面一定要看到的東西。

## 還沒做的事

- `PaperEngine` 目前要從 `at_core::backtest::PaperEngine` 取用，`lib.rs` 還沒有把它
  加進 `pub use`（這一步刻意只改一個檔案）。5.2 真的開始用它的時候再加。
- 餵進來的 K 線是不是「已經收盤」由呼叫端負責。5.2 會用 4.5 的 `k.x` 欄位過濾，
  未收盤的 K 線只能拿來畫圖，不可以餵給 `on_bar`。
- 開始／停止、斷線續接、查詢未實現損益是 5.3 的事；引擎現在只提供
  `cash()`／`position()`／`trades()`／`liquidations()` 四個最小的查詢。
- 引擎回錯誤之後帳本已經不完整，現在的約定是「不要再繼續餵」。模擬交易要怎麼處理
  （停掉整個執行？還是跳過這根？）留給 5.3 決定。
