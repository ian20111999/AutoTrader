# 5.4 桌面 App「模擬交易」頁面

5.1-5.3 把模擬交易的引擎、接線、開始/停止都做好了，但只存在於 Rust 測試裡——沒有任何畫面可以
按。這一步把它接到桌面 App，新增「模擬交易」分頁：選策略、選交易對/週期、按「開始模擬」，
畫面即時顯示權益曲線與部位，按「停止模擬」結束。到這一步，ROADMAP 第 5 節（模擬交易）全部完成。

這一步完全不可能送出訂單：`at_paper_trading::spawn` 只讀公開行情、只呼叫記帳引擎，沒有引入
`at-binance`。

## 做了什麼

### 一、Tauri command 是請求/回應式的，怎麼回傳一條持續的 channel

`PaperTradingHandle.updates` 是一個 `mpsc::Receiver`：只要模擬交易還在跑，它就會不斷收到新的
`PaperUpdate`。但 Tauri command 是「前端呼叫一次、Rust 回一次」的模式，沒辦法直接把這種持續的
東西當回傳值送出去。

做法是 `start_paper_trading` 開一條背景執行緒，把**整個** `PaperTradingHandle`（包含
`updates`）搬進去，逐則消費、透過 Tauri 的事件系統轉發：

```rust
fn forward_updates(app: AppHandle, paper: PaperTradingHandle) {
    let state = app.state::<PaperTradingState>();
    for update in paper.updates {
        let event = /* 更新共用狀態、組出要送的事件 */;
        let _ = app.emit("paper-trading-update", &event);
    }
}
```

前端用 `@tauri-apps/api/event` 的 `listen("paper-trading-update", callback)` 訂閱，每收到一則
就更新畫面。

### 二、「停止」command 為什麼不呼叫 `PaperTradingHandle::stop()`

`stop()`／`latest_snapshot()` 都要 `&PaperTradingHandle`，但整個 handle 已經被搬進背景執行緒，
`stop_paper_trading` 這個 command 拿不到它——沒有辦法兩邊同時擁有同一個值。

解法沿用 5.3 已經驗證過的設計：`at_paper_trading::spawn` 內部做的第一件事就是跟
`MarketStreamHandle::stop_flag()` 要一份停止旗標的 `Arc` 複本。**我們自己在呼叫 `spawn` 之前，
先跟同一個 `MarketStreamHandle` 也要一份**：

```rust
let stream = spawn_stream(kline_stream(&symbol, interval));
let stop_flag = stream.stop_flag();       // 我們自己留一份
let paper = spawn_paper(stream, strategy, &config)?;  // spawn_paper 內部也會拿一份，同一個 Arc
```

`stop_flag` 存進 Tauri app state。`stop_paper_trading` 只是 `stop_flag.store(true, Relaxed)`
——效果跟呼叫 `paper.stop()`完全一樣（本來就是同一個 `AtomicBool`），但不需要碰
`PaperTradingHandle` 的私有欄位（本來也碰不到）。「目前狀態」也是同樣的理由：背景執行緒每收到
一則 `Bar` 就順手把 DTO 寫進 app state，`paper_trading_status` 直接讀那份存檔，不呼叫
`latest_snapshot()`。

### 三、驗證跟開始行情連線的先後順序

`spawn_stream` 一呼叫就會真的開始連 WebSocket（背景執行緒馬上開始連線、重連）。如果驗證
（策略參數、起始資金）擺在連線**之後**才做，驗證失敗時就會留下一條沒人管的孤兒連線——沒有人
拿著那個 `stop_flag`。

所以 `validate_request`（純函式，不碰網路）把所有能在本地驗證的東西都擋在連線之前：交易對格式、
K 線週期、策略參數、**起始資金必須大於 0**。最後一項特別重要：`PaperEngine::new` 本來就會擋
`initial_capital <= 0`，但那個檢查在 `spawn_paper` 內部，這時行情已經連上了。自己先擋一次，
`spawn_paper` 理論上就不會再失敗——但還是留著錯誤處理，失敗就用已經拿到的 `stop_flag` 把連線
關掉，不留孤兒。

### 四、狀態機：`Idle` / `Running` / `Stopped` / `Failed`

```rust
enum RunState { Idle, Running, Stopped, Failed(String) }
```

`Stopped` 和 `Failed` 的意思完全不同（5.3 就定義好了，這一步是畫面第一次真的把它們分開處理）：

| 狀態 | 帳本 | 畫面 |
|---|---|---|
| `Running` | 持續更新 | 綠色「執行中」文字 + 即時曲線/統計 |
| `Stopped` | **完整**，只是不再更新 | 一般文字「已停止模擬交易」，曲線留著 |
| `Failed(msg)` | **不完整**，從失敗那一刻起不可信 | 紅色警告，講清楚「帳本已經不可信」 |

套用邏輯（`apply_update`）刻意寫成純函式，不碰 Tauri/背景執行緒，方便直接測試狀態機對不對：

```rust
fn apply_update(inner: &mut Inner, update: PaperUpdate) -> PaperUpdateEvent
```

### 五、前端頁面

新分頁「模擬交易」加在側邊導覽第四項（策略庫／回測／比較／**模擬交易**／設定）。表單重用
3.5 選好的全域 `strategyConfig`（跟回測頁面一樣的模式：沒選策略就顯示「請先到策略庫選」），
另外填交易對、K 線週期（沿用 3.6 的 `INTERVAL_OPTIONS`）、虛擬起始資金。

執行中：監聽 `paper-trading-update` 事件，`bar` 更新累積成曲線（重用 3.6 的
`EquityCurveChart`）、更新權益/現金/部位/成交筆數/強制平倉次數；`stopped` 顯示一般狀態；
`failed` 顯示紅色警告。頁面掛載（含使用者切分頁再切回來）時額外查一次
`paper_trading_status`，把最後已知狀態補上畫面，不用等下一個事件才有東西可看——但這只能補回
**一個點**，因為 `latest_snapshot`／`paper_trading_status` 本來就只回「目前狀態」，不回完整
歷史（5.3 的設計就是這樣，channel 才是事件流）。

CSS 幾乎沒有新增：表單、結果區塊直接重用 `.backtest-form`／`.backtest-result` 等既有類別
（回測頁面跟模擬交易頁面本來就是同一種「選資料+策略 → 跑 → 看結果」版面），只新增了統計格線
跟「執行中」的綠色文字兩條規則。

## 範圍取捨（對照設計稿 `PaperTrading.dc.html`）

設計稿畫的是一個相當完整的「多重模擬 session」畫面。底層 `PaperTradingHandle` 目前只支援單一
session、單一交易對，所以照 3.x 的慣例砍掉支撐不了的部分：

| 設計稿有 | 這一步砍掉的原因 |
|---|---|
| 多個模擬 session 頁籤（同時跑好幾個策略） | Tauri app state 只有一個 `Mutex<Option<...>>`，一次只能跑一場；要做多開需要先把 state 改成 map，超出這一步範圍 |
| 「模擬 vs 回測」疊圖比較、差距分析 | 需要額外跑一次同期回測並對齊時間軸，是全新功能，不是這一步的資料橋接 |
| 多幣別部位表（BTCUSDT 多、ETHUSDT 空同時顯示） | 策略/引擎目前是單一交易對；`PaperSnapshot.position` 是單一數字 |
| 逐筆成交紀錄表（時間/方向/成交價/手續費/滑價） | `PaperSnapshot` 只回累計後的 `trades: usize`（筆數），沒有保留逐筆明細 |
| 手續費/滑價/資金費分項金額 | 引擎沒有把這些拆開回傳，只有 `cash`/`equity` 這種聚合後的數字 |
| 「暫停」（跟停止分開的動作） | `PaperTradingHandle` 只有 `stop()`，是單向的；5.3 的文件就寫明暫停/繼續是完全不同的需求 |

## 怎麼驗證

```bash
# Rust
cd app/src-tauri
cargo fmt --all
cargo clippy --all-targets -- -D warnings
cargo test

# 前端
cd app
npm run lint
npm test
npm run build

# 根目錄（確認既有 crate 不受影響）
cargo test
```

真實連線測試（需要網路，預設不跑）：

```bash
cargo test -p app -- --ignored --nocapture paper_trading
```

```

test paper_trading::tests::real_binance_stream_produces_well_formed_snapshots_and_stops_cleanly ... ok
```

（真的連上 BTCUSDT 1 分鐘 K 線、收到一則真實快照、按停止乾淨收工——用的是 `validate_request` +
`apply_update` 這兩個純函式跑真實資料，不需要另外搭一個假的 Tauri App。）

前端測試分兩份：

- `PaperTrading.test.tsx`：跟專案既有慣例一樣，手動 `vi.mock` `@tauri-apps/api/core` 和
  `@tauri-apps/api/event`，驗證表單/驗證錯誤/事件對畫面的影響。
- `PaperTrading.integration.test.tsx`：改用 Tauri 官方的 `@tauri-apps/api/mocks`
  （`mockIPC` + `shouldMockEvents: true`），讓 `invoke`/`listen`/`emit` 走真正的實作，只換掉
  最底層的 `window.__TAURI_INTERNALS__`，驗證「開始→即時更新→停止」與「Failed 顯示警告」這兩條
  完整路徑。專案裡沒有 Playwright（3.1-4.6 全部只用 Vitest），這是同一套工具能做到的最接近端對
  端的驗證，不必為了這一步另外引入一個新框架。

## 建議閱讀順序

1. `app/src-tauri/src/paper_trading.rs` 開頭的模組文件註解：為什麼要背景執行緒、為什麼「停止」
   不呼叫 `PaperTradingHandle::stop`。
2. 同檔的 `validate_request`：所有能在連線之前擋掉的錯誤都在這裡。
3. 同檔的 `start_paper_trading`：`stop_flag` 什麼時候被要一份、`spawn_paper` 失敗時怎麼收拾。
4. 同檔的 `apply_update`／`status_dto`：狀態機本身，純函式、不碰 I/O。
5. `app/src/PaperTrading.tsx` 的三個 `useEffect`：讀策略清單、掛載時查狀態、訂閱事件。

## 動手試試看

1. 把 `app/src-tauri/src/paper_trading.rs` 裡 `validate_request` 的「起始資金必須大於 0」那段
   檢查註解掉，跑 `cargo test -p app`——`zero_capital_is_rejected_before_touching_the_network`
   會失敗。這就是「驗證要擋在連線之前」這個設計決定的證據。
2. 開發模式跑起來（`npm run tauri dev`），切到「模擬交易」分頁選一個策略、按「開始模擬」，
   等一分鐘看第一個點出現；按「停止模擬」，再切到別的分頁、切回來——應該直接看到剛剛的最後
   狀態，不必等下一個事件。
3. 開發模式下跑到一半，直接把電腦斷網幾秒再接回來：`at-market-stream` 的重連機制（4.5）會自動
   運作，畫面上不會有任何特別的錯誤（未收盤的重複 K 線會被引擎的時間單調性檢查擋掉，
   詳見 5.2）。

## 還沒做的事

- **一次只能跑一場模擬**。要同時觀察多個策略需要把 Tauri app state 從
  `Mutex<Option<PaperTradingHandle>>` 改成用某種 key（例如 session id）索引的 map，是之後才要
  做的事。
- **沒有歷史模擬交易紀錄保存**。關掉 App 或按停止之後，這一場模擬的曲線就只存在畫面的 React
  state 裡，沒有寫進任何檔案；下次開啟只能看到「最後一個點」（`paper_trading_status` 的限制），
  看不到完整曲線。
- **交易對選擇只是一個文字輸入框**，沒有像回測頁面那樣的下拉選單或驗證交易對是否存在；打錯字
  只會在連線失敗或收不到任何行情時才發現。
- **逐筆成交明細、手續費/滑價/資金費分項** 都沒有：`PaperSnapshot` 目前只回累計後的數字。
