# 4.4 下單規則同步

把 1.3 的 `SymbolRules` 從「手寫的近似值」換成「Binance 現在真正在用的規則」：24 小時打一次
`GET /api/v3/exchangeInfo`，存到本機，打不通就沿用上次的值並標記成過期。

這一步只打**公開端點**——不需要 API 金鑰、不簽名、不讀 Keychain，也沒有任何送出訂單的程式碼
路徑。

## 做了什麼

`crates/binance-client/src/lib.rs`（4.2 的 client）新增公開端點的路徑：

- `public_get(path, params) -> Result<String, BinanceError>`：不帶 `X-MBX-APIKEY`、不簽名的 GET。
- `join_params` / `get_text`：簽名端點和公開端點共用的「接查詢字串」與「送出 GET + 讀回內文」，
  `signed_get` 改用同一份，行為不變（官方簽名範例的測試與真實 API 測試都還是綠的）。

`crates/account-sync/src/rules.rs`（新模組，掛在 4.3 的同一個 crate 底下）：

- `sync_symbol_rules(base_dir, symbol) -> Result<SyncedRules, RulesSyncError>`：整條同步流程。
- `SyncedRules { rules, synced_at_ms, freshness }`：規則本身 + 什麼時候拿到的 + 新不新鮮。
- `RulesSyncError::NoCachedRules` / `BadResponse` / `SystemClock`。
- `rules::cache_path(base_dir, symbol)`：`<base_dir>/symbol_rules_<SYMBOL>.json`。
- `Freshness` 和 `CACHE_TTL_MS` 直接沿用 4.3 的，沒有再定義一份。

用起來像這樣：

```rust
let symbol = Symbol::new("BTCUSDT")?;
let synced = at_account_sync::rules::sync_symbol_rules("data", &symbol)?;
match synced.freshness {
    Freshness::Fresh => { /* 24 小時內同步成功的規則，可以直接用 */ }
    Freshness::Stale { age_ms } => { /* 提醒使用者：這是 age_ms 毫秒前的舊規則 */ }
}
let price = synced.rules.round_price(Side::Buy, want_price)?;
let qty = synced.rules.qty_for_quote(budget, price)?;
synced.rules.check(price, qty)?;   // 1.3 的合規檢查，現在吃的是真實規則
```

## 為什麼這樣設計

### 公開端點為什麼另外開一條路，不是塞進 `signed_get`

`exchangeInfo` 在 Binance 文件裡的安全等級是 `NONE`：不需要金鑰、不需要簽名。硬塞進簽名邏輯
會有兩個實際壞處：

1. **每查一次公開資料就要讀一次 Keychain**，macOS 會跳授權對話框（4.1/4.3 都踩過這個坑）。
   明明是一份公開資料，卻要使用者按一次「允許」，說不過去。
2. **金鑰的接觸面無謂變大**。`public_get` 寫成自由函式、不是 `BinanceClient` 的方法，所以它
   在型別上根本拿不到金鑰——不是「我記得不要傳」，是「傳不進去」。

`signed_get` 唯一的改動是把 HTTP 那段換成共用的 `get_text`。狀態碼的錯誤訊息在兩條路上不一樣：
簽名端點失敗會提示「請確認金鑰與權限是否正確」，公開端點不會——公開端點的 400 跟金鑰無關，
叫使用者去檢查金鑰只會把人帶去錯的地方找問題。

### filters 怎麼對到 `SymbolRules`（這一步最容易出錯的地方）

Binance 不是直接給你五個欄位，而是給一個 `filters` 陣列，每個元素有自己的 `filterType`。
對照表（語意來自官方文件
<https://developers.binance.com/docs/binance-spot-api-docs/filters>，
實際欄位用 `GET /api/v3/exchangeInfo?symbol=BTCUSDT` 的真實回應核對過）：

| `SymbolRules` 欄位 | 來源 | 官方定義 |
|---|---|---|
| `tick_size` | `PRICE_FILTER.tickSize` | 價格必須是它的倍數（`price % tickSize == 0`）|
| `step_size` | `LOT_SIZE.stepSize` | 數量必須是它的倍數（`quantity % stepSize == 0`）|
| `min_qty` | `LOT_SIZE.minQty` | `quantity >= minQty` |
| `max_qty` | `LOT_SIZE.maxQty` | `quantity <= maxQty` |
| `min_notional` | `NOTIONAL.minNotional`，沒有才退 `MIN_NOTIONAL.minNotional` | `price * quantity >= minNotional` |

三個容易踩的地方：

- **`MARKET_LOT_SIZE` 不是 `LOT_SIZE`**。它也有 `minQty`/`maxQty`/`stepSize`，但講的是市價單的
  限制，而且 BTCUSDT 現貨的 `stepSize` 是 `0`。只看欄位名不看 `filterType` 的寫法會撿到它，
  所有限價單的數量取整就會失效。程式一律先認 `filterType`。
- **`NOTIONAL` 和 `MIN_NOTIONAL` 是新舊兩代**。`NOTIONAL` 是現行版本（同時給最低與最高金額），
  `MIN_NOTIONAL` 是舊版（只有最低）。兩者的 `minNotional` 語意相同，部分交易對與測試網還在給
  舊的，所以兩個都認、現行的優先。
- **`0` 在 Binance 的意思是「這條規則停用」**，不是「跳動為零」。1.3 的 `SymbolRules` 拿
  `tick_size`/`step_size` 當除數，沒有「停用」這個狀態。與其偷偷代一個假值進去，程式選擇直接
  報錯——正在交易中的現貨交易對不會是 0，真的拿到 0 就代表撿錯 filter 了。

`minPrice`/`maxPrice`/`maxNotional` 和各種張數上限沒有收：1.3 的 `SymbolRules` 沒有對應欄位，
而為了存它們去動回測引擎的核心型別，代價遠大於好處。真的需要（例如要擋「價格超過上限」）再回頭
加，那時候是 1.3 的事，不是這一步的事。

### 沒有動 1.3 的 `SymbolRules`

`SymbolRules` 是回測引擎的核心型別，這一步只 `use` 它、只呼叫既有的 `SymbolRules::new`。
「這份規則什麼時候拿到的」放在外層的 `SyncedRules.synced_at_ms`，不是塞進 `SymbolRules` 多一個
欄位——同步機制的時間戳不該滲進一個被回測、模擬、實盤共用的資料型別裡。

（和 4.3 不一樣：`FeeSchedule` 本來就留了 `synced_at` 欄位，所以那一步是填既有欄位。）

### 快取只存五個數字，不存整包回應

不帶 `symbol` 參數時 `exchangeInfo` 會回傳上千個交易對、好幾 MB 的 JSON。程式做了兩件事把它縮小：

1. **打 API 時就帶 `symbol=BTCUSDT`**，讓 Binance 只回一個交易對。
2. **解析後只留 `SymbolRules` 用得到的五個數字**才寫進快取，其餘欄位丟掉。

快取檔裡的數字照 Binance 的原樣存成字串（`"0.01000000"`）再自己 `parse` 成 `Fixed`：`Fixed` 住在
零外部依賴的 `at-core`，不能掛 serde 的 derive，收字串也比較好回報「是哪一欄壞掉」。這點和 4.3 一致。

### 為什麼放進 `at-account-sync`，不開新 crate

4.3 的交接筆記已經寫明這個判斷：下單規則同步和費率同步是**一模一樣的形狀**（從 Binance 拿設定 →
存本機 → 24 小時快取 → 失敗沿用舊值），開第二個長得幾乎一樣的 crate 只是多一份 `Cargo.toml`。
`Freshness` 和 `CACHE_TTL_MS` 直接共用，不重新定義一份。

唯一刻意重複的是 `age_ms` / `now_ms` 兩個各 5 行的時間工具：兩邊的錯誤型別不同
（`FeeSyncError` / `RulesSyncError`），為了 8 行共用而讓費率同步反過來依賴這個模組並不划算。

### ponytail：刻意沒做的事

- **只做 BTCUSDT 一個交易對、只做現貨**：和 4.3 一致。合約的 `/fapi/v1/exchangeInfo` 等真的要接
  合約帳戶再說。
- **`Stale` 沒有附上失敗原因**：目前只帶「多舊」，之後 UI 要顯示「同步失敗：沒網路」再加。
- **快取寫入失敗直接吞掉**：規則這次已經拿到手、照樣回傳，寫不進去的代價只是下次多打一次 API。

### 兩份測試資料，各有各的工作

- `LIVE_BTCUSDT`：2026-09-29 真的從 Binance 抓回來的回應（含 `ICEBERG_PARTS`、`MARKET_LOT_SIZE`、
  `PERCENT_PRICE_BY_SIDE` 這些不相干的 filter）。確認程式吃得下真實格式。
- `DISTINCT`：一樣的格式，但**每個數字都不一樣**。因為真實回應裡 `minQty` 和 `stepSize` 剛好
  都是 `0.00001`——對調了也看不出來。`MARKET_LOT_SIZE` 故意排在 `LOT_SIZE` 前面，只看欄位名的
  寫法會先撿到它。

### 確認測試不是虛的：故意改壞四個地方

綠燈只證明「現在是綠的」，不證明「壞掉時會紅」。四個關鍵判斷分別改壞，確認對應的測試真的失敗
（改完都還原了，`diff` 確認過和原檔完全一致）：

| 故意改壞的地方 | 哪個測試抓到 |
|---|---|
| 24 小時邊界 `age < TTL` 改成 `age <= TTL` | `cache_exactly_24h_old_is_refetched` |
| 退回舊值時把 `Stale` 改成 `Fresh`（謊報新鮮） | `api_failure_falls_back_to_the_cached_value...` |
| `LOT_SIZE` 撿成 `MARKET_LOT_SIZE` | `every_filter_field_maps_to_the_right_slot`、`market_lot_size_is_never_used_as_lot_size`（連帶共 13 個測試失敗，實測驗證過）|
| `stepSize` 和 `minQty` 對調 | `every_filter_field_maps_to_the_right_slot` |

最後一個特別值得看：**只有一個測試抓到**，而且靠的是 `DISTINCT` 那份資料。如果只拿真實回應來
測，這個 bug 會完全無聲通過——真實的 `minQty` 和 `stepSize` 剛好一樣。

BTCUSDT 現貨的價格跳動 0.01 USDT、最小下單金額 5 USDT，和 Binance 網頁上看到的一致。1.3 當初手寫

## 建議閱讀順序

1. `crates/binance-client/src/lib.rs` 的 `public_get`：為什麼公開端點要和簽名端點分開。
2. `crates/account-sync/src/rules.rs` 的 `SymbolInfoJson::to_rules_json`：filters 怎麼對到
   `SymbolRules`，這是這一步的重點。
3. `sync_symbol_rules_with`：整條流程的骨架，和 4.3 的 `sync_spot_fees_with` 幾乎一模一樣，
