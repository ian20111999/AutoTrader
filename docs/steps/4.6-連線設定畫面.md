# 4.6 桌面 App「連線設定」畫面

提前完成（只依賴 4.1 的 `KeychainStore`，不依賴還沒做的 4.2-4.5）。這一步**完全不連
Binance 網路**，只是把 4.1 的 OS 安全儲存區模組包成使用者在 App 內能操作的表單，取代之前
「設定」分頁裡的空白佔位文字。

## 做了什麼

新增/修改六個檔案：

- `app/src-tauri/src/settings.rs`：三個 Tauri command——`save_binance_credentials`（存）、
  `binance_credentials_status`（查「有沒有設定」）、`clear_binance_credentials`（清除），
  包 4.1 `at_secrets::KeychainStore`。
- `app/src-tauri/Cargo.toml`：加一行 `at-secrets = { path = "../../crates/secret-store" }`，
  只 `use` 既有公開 API，沒有改 `crates/secret-store` 的任何程式碼。
- `app/src-tauri/src/lib.rs`：註冊 `mod settings` 與三個新 command。
- `app/src/settingsTypes.ts`：對應 `CredentialStatus` 的 TypeScript 型別。
- `app/src/Settings.tsx`：連線狀態顯示 + 更新表單 + 清除按鈕。
- `app/src/App.tsx`：「設定」分頁換成 `<Settings />`，拿掉舊的版本號佔位文字。

## 為什麼要這樣做

### Rust 端：兩個欄位一起驗證、一起存、一起 trim

`save_with` 先把 `api_key`/`api_secret` 都 `trim()` 過，任一個 trim 後是空字串就直接回錯誤
訊息，**不呼叫任何 `store.set`**——避免「secret 驗證失敗，但 key 已經先存進去」的半套狀態。

trim 不只是為了擋空白輸入：使用者從 Binance 後台複製金鑰時很容易連前後空白或結尾換行一起
複製進來，如果原樣存進 Keychain，4.2 做 HMAC 簽名時會直接簽名失敗，而且錯誤訊息完全看不出
是這個原因（看起來像金鑰本身不對）。現在存進去的就是乾淨的字串，把這個坑消滅在 4.2 開始
之前。

### 安全設計：狀態只回布林值,不回內容

`binance_credentials_status` 回傳 `CredentialStatus { apiKeySet, apiSecretSet }`，只有兩個
布林欄位，刻意不經過任何會暴露 `SecretValue` 內容的路徑——就算前端程式碼想印出這個回傳值,
印出來的也只有 `true`/`false`,沒有金鑰內容可以洩漏。這個模組完全沒有「顯示已存金鑰內容」的
功能,業界標準做法是密鑰只能覆蓋、不能讀出來顯示。

三個 command 的參數、回傳值、錯誤訊息都不含憑證內容：
[`at_secrets::SecretError`] 本來就只回固定中文訊息（4.1 的既有設計），這裡直接
`.to_string()` 轉成 command 的 `Err`；本專案目前唯一裝的 Tauri plugin 是
`tauri-plugin-opener`，不會記錄 command 參數，模組本身也完全沒有呼叫
`log`/`println!`/`eprintln!`/`console.log`。有一條測試
（`error_messages_never_contain_the_credential_value`）專門驗證：故意傳一個「一看就是
密鑰內容」的字串進去觸發錯誤，斷言錯誤訊息裡不包含這個字串。

前端 `Settings.tsx` 存完之後立刻清空兩個輸入框（`setApiKey(""); setApiSecret("")`），不讓
剛輸入的值繼續留在畫面或 state 裡比需要的時間更久。

### 前端表單：用原生 `required` 擋空白，不重複寫一份驗證

兩個 `<input type="password" required>` 靠瀏覽器原生 constraint validation 擋「按儲存但欄位
是空的」，不需要在 `Settings.tsx` 另外寫一份 JS 驗證邏輯重複 Rust 端已經做的
「不能是空白」判斷——ladder 規則「平台原生有就不用另外寫」的應用。空白但非空字串（例如只打
了空白鍵）的邊界情況原生 `required` 擋不住，這種情況交給 Rust 端的 `trim().is_empty()` 當
最後一道防線,錯誤訊息會顯示在表單上。

`type="password"` 讓輸入內容在畫面上被遮蔽（旁人看不到），這是唯一需要的「輸入保護」；
`autoComplete="off"` 避免瀏覽器把 API 金鑰存進自動填表記錄。

### 清除前用瀏覽器原生 `confirm()`

清除是不可逆動作，`handleClear` 用原生 `window.confirm()` 攔一次，使用者按「取消」就直接
`return`，不呼叫任何 command——不需要自己刻一個確認對話框元件，原生 `confirm()` 就是一個
會擋住後續程式碼執行、使用者一定會看到的同步對話框，符合這裡的需求。

### 狀態機：三個獨立的 loading/error 狀態

查詢狀態（`statusError`）、儲存（`saveStatus`: idle/saving/success/error）、清除
（`clearStatus`: idle/clearing/error）各自獨立，不共用一個全域的 loading flag——三個操作
可能在使用者操作下交錯發生（例如儲存成功後立刻又按清除），共用一個 flag 會讓某個操作的
loading 狀態被另一個操作蓋掉。這跟 `Backtest.tsx` 的 `Status` 三態切換是同樣的設計精神，
只是這裡有三個獨立的操作需要各自的三態。

## 怎麼驗證

```bash
# Rust 端
cd app/src-tauri
cargo fmt --all
cargo clippy --all-targets -- -D warnings
cargo test          # 10 個 settings:: 測試全過，其餘 16 個既有測試不受影響

# 前端
cd app
npm test             # Vitest：73 個測試全過（60 個既有 + 13 個新增的 Settings.test.tsx）
npm run lint          # ESLint 零錯誤
npm run build         # tsc + vite build 成功
```

Rust 端測試全部用 `InMemoryStore`（4.1 既有的測試替身），**沒有碰過使用者存在 macOS
鑰匙圈裡的正式 `binance-readonly-*` 憑證**，也沒有在真實鑰匙圈留下任何測試資料。前端測試
的假憑證字串固定用 `fake-test-key-12345`/`fake-test-secret-67890`，格式上一看就不是真的
金鑰。

離線／實跑驗證：跟 3.6 同樣的模式，用 Playwright MCP 開 `npm run dev`，掛
`window.__TAURI_INTERNALS__.invoke` 的 mock（維護一個記憶體內的 `saved` 狀態，`status`/
`save`/`clear` 三個 command 互相呼應），實際走了完整流程：

1. 切到「設定」分頁 → 狀態顯示「API Key：未設定」「API Secret：未設定」。
2. 填入假憑證（`fake-test-key-12345`/`fake-test-secret-67890`，`type="password"` 遮蔽）→
   點「儲存」→ 顯示「已儲存。」→ 狀態立刻變成「已設定」「已設定」→ 兩個輸入框被清空。
3. 確認 mock 收到的 `save_binance_credentials` 呼叫參數正確是
   `{apiKey: "fake-test-key-12345", apiSecret: "fake-test-secret-67890"}`（camelCase,
   對應 Tauri 預設的 command 參數命名慣例,不用 `rename_all`）。
4. 點「清除已儲存的金鑰」→ 跳出瀏覽器原生 `confirm()` 對話框,訊息是「確定要清除已儲存的
   Binance API 金鑰嗎？此動作無法復原。」→ 確認 → 狀態變回「未設定」「未設定」。
5. 檢查瀏覽器 console：全程沒有任何一筆訊息包含假憑證字串或任何錯誤/警告。

根目錄 `cargo fmt --all --check`、`cargo clippy --all-targets -- -D warnings`、
`cargo test`（跨 `crates/core`/`crates/downloader`/`crates/engine`/`crates/secret-store`
四個 crate）：全部通過，這次改動完全沒有碰 `crates/` 任何一個 crate 的程式碼（只在
`app/src-tauri/Cargo.toml` 加了一行既有 crate 的依賴宣告）。

## 給 4.2（真的連 Binance）的銜接說明

4.2 要做 HMAC-SHA256 簽名時，讀金鑰的方式就是直接建一個 `at_secrets::KeychainStore`，呼叫
`store.get("com.autotrader.app.binance-readonly-api-key", "autotrader")` 跟
`store.get("com.autotrader.app.binance-readonly-api-secret", "autotrader")`
（`settings.rs` 頂部的 `SERVICE_API_KEY`/`SERVICE_API_SECRET`/`ACCOUNT` 三個常數就是這兩組
service/account 字串，4.2 可以直接沿用或搬到共用的地方）。拿到的 `SecretValue` 呼叫
`.expose()` 取出字串去組簽名字串、算 HMAC，簽完之後就讓這個字串的生命週期盡快結束，不要
存進任何長生命週期的 struct 欄位或印出來 debug。如果 4.2 執行時發現金鑰根本沒設定
（`get` 回傳 `None`），錯誤訊息應該引導使用者回到 4.6 這個「設定」分頁去輸入，而不是一個
抽象的「認證失敗」。

## 建議閱讀順序

1. `app/src-tauri/src/settings.rs`：三個 command 的邏輯與 `save_with`/`status_with`/
   `clear_with` 三個純函式（跟 command 分開方便直接用 `InMemoryStore` 測）
2. `app/src/settingsTypes.ts`：對應的前端型別
3. `app/src/Settings.tsx`：三組獨立的 loading/error 狀態怎麼切換、表單怎麼用原生
   `required` 擋空白、清除前的原生 `confirm()`

## 動手試試看

1. 把 `Settings.tsx` 的 `window.confirm(...)` 訊息改一改，跑 `npm run dev` 點一次「清除」
   看新訊息有沒有出現。
2. 在 `settings.rs` 的 `save_trims_surrounding_whitespace_before_storing` 測試裡，把輸入
   字串換成中間夾空白（例如 `"fake key"`）而不是前後空白，想想看 `trim()` 會不會處理這種
   情況、應不應該處理。
