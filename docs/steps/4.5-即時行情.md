# 4.5 即時行情 WebSocket 連線

連上 Binance **公開**行情 WebSocket，持續接收即時價格（ticker）與即時 K 線（kline），斷線後用
指數退避自動重連。這一步做完，ROADMAP 第 4 節（Binance 唯讀連線）全部完成。

這一步不需要 API 金鑰——市場行情是公開資料，不會碰 Keychain、不會跳授權對話框，也沒有任何
送出訂單的程式碼路徑。

## 做了什麼

新開一個 crate：`crates/market-stream`（package 名 `at-market-stream`），只有一個檔案
`src/lib.rs`。

對外的公開介面：

```rust
pub fn ticker_stream(symbol: &str) -> String;          // "btcusdt@ticker"
pub fn kline_stream(symbol: &str, interval: Interval) -> String; // "btcusdt@kline_1m"
pub fn spawn(stream_name: impl Into<String>) -> MarketStreamHandle;

pub struct MarketStreamHandle {
    pub events: std::sync::mpsc::Receiver<MarketEvent>,
    // ...
}

pub enum MarketEvent {
    Ticker(TickerUpdate),
    Kline(KlineUpdate),
}

pub struct TickerUpdate { pub symbol: Symbol, pub last_price: Fixed, pub event_time_ms: i64 }

pub struct KlineUpdate {
    pub symbol: Symbol,
    pub interval: Interval,
    pub bar: Bar,          // 1.2 的 Bar，開高低收量
    pub is_closed: bool,   // 對應 Binance 的 k.x：這根 K 線收盤了沒
    pub event_time_ms: i64,
}
```

用起來像這樣：

```rust
let handle = at_market_stream::spawn(at_market_stream::kline_stream("BTCUSDT", Interval::M1));
for event in handle.events {
    match event {
        MarketEvent::Kline(k) if k.is_closed => {
            // 這根真的收盤了，可以當成 1.2 的歷史 K 線存起來
        }
        MarketEvent::Kline(_) => { /* 還在形成中，只用來更新畫面，不要存 */ }
        MarketEvent::Ticker(t) => { /* 更新畫面上的即時價格 */ }
    }
}
```

`spawn` 內部開一條背景 OS 執行緒，跑「連線 → 阻塞讀取 → 解析 → 送進 channel → 斷線就用
[`Backoff`] 退避重連」這個迴圈，呼叫端只拿到一個標準函式庫的 `mpsc::Receiver`。

## 為什麼這樣設計

### 同步 thread + channel，不是 tokio async

這個專案目前完全是同步、阻塞式的：`at-binance`／`at-downloader` 用 `ureq`，沒有任何 async
runtime。WebSocket 是長連線、需要持續接收訊息，常見的兩條路：

- **(a) 同步 WebSocket + 專用背景執行緒**（這次選的）：`tungstenite`（阻塞式 API，不需要
  tokio）搭配一條 `std::thread`，對外只露出 `mpsc::Receiver`。
- **(b) 真正的 async**：`tokio` + `tokio-tungstenite`。

選 (a)：為了一條 WebSocket 連線把整個專案從同步改成 async，代價是之後每個呼叫端（回測引擎、
桌面 App 的 Tauri command）都要決定要不要進入 async context，這是 framework 級的架構改變。
(a) 把「這裡是長連線」封裝在一條背景執行緒裡，對外仍然是簡單的同步介面，量（一條或幾條行情
串流）也用不到 async 帶來的併發優勢。這個判斷在派工指示裡已經定調：選不引入新框架的方向
（(a)）不需要另外升級確認，只有真的要選會引入 tokio 的 (b) 才需要標記 🔴 停下來問——不是
逐項技術選型都個別問過使用者，是「有沒有跨過框架級門檻」這個既有判準本身已經涵蓋了這個決定。

### `tungstenite` 走 `rustls-tls-webpki-roots`，不是 `native-tls`

`ureq`（已經在用）本來就透過 `rustls` + `webpki-roots` 做 TLS（`Cargo.lock` 裡已經有
`rustls 0.23`、`ring`、`webpki-roots`）。`tungstenite` 的 TLS 後端要另外選 feature，選
`rustls-tls-webpki-roots` 而不是 `native-tls`：重用已經在依賴樹裡的同一套 TLS 實作，不會
另外多拉一條 `native-tls`（macOS Secure Transport）進來、多一個要維護的攻擊面。

### 一個意料之外的 rustls 陷阱：process 級 `CryptoProvider`

`cargo build` 沒事、單元測試（不連網路）也沒事，但第一次真的打 `#[ignore]` 測試連上
Binance 時整個 panic：

```
Could not automatically determine the process-level CryptoProvider from Rustls crate features.
Call CryptoProvider::install_default() before this point to select a provider manually...
```

rustls 0.23 之後，即使整個依賴樹裡只編進一種加密後端（這裡是 `ring`，`Cargo.lock` 裡沒有
`aws-lc-rs`），也不會自動幫你在 process 裡裝一個預設的 `CryptoProvider`——用到 TLS 之前
一定要有人手動裝一次。`ureq` 自己內部有裝，但那是它自己那條路徑的事，不會影響
`tungstenite` 這條完全獨立的連線路徑。

修法：`connect_real` 第一次連線前呼叫一次（`std::sync::Once` 保護，裝過就不再裝，也不管
裝不裝得成——已經有人裝過同一個也沒關係）：

```rust
fn ensure_crypto_provider() {
    static INSTALLED: std::sync::Once = std::sync::Once::new();
    INSTALLED.call_once(|| {
        let _ = rustls::crypto::ring::default_provider().install_default();
    });
}
```

多加了一個直接依賴 `rustls = { version = "0.23", default-features = false, features =
["ring"] }`（本來就是 `tungstenite` 的間接依賴，版本沒有變，只是讓 `rustls::crypto::ring`
這個模組路徑在這個 crate 裡能直接用）。

這正是「連真的網路才會出事」的例子——`cargo test`（不含 `--ignored`）完全測不到這個問題，
只有真的打一次 Binance 才會發現。

### Kline 收盤／未收盤：`k.x` 欄位

查證來源：<https://developers.binance.com/docs/binance-spot-api-docs/web-socket-streams>
（Binance 官方 WebSocket Streams 文件）。Kline 串流的訊息結構：

```
{ "e": "kline", "E": <事件時間>, "s": "<symbol>",
  "k": { "t": <開盤時間>, "T": <收盤時間>, "i": "<週期>",
         "o": "<開>", "h": "<高>", "l": "<低>", "c": "<收>", "v": "<量>",
         "x": <是否已收盤>, ... 其餘欄位這裡用不到 } }
```

Binance 每秒左右就會推一則「這根還在形成中」的訊息（`x: false`），同一根的 `t`（開盤時間）
不變、`o`/`h`/`l`/`c`/`v` 會一直更新，直到真正收盤那一刻才會收到 `x: true` 的最後一則。
`KlineUpdate::is_closed` 直接對應 `k.x`；1.2 的歷史 K 線只應該收 `is_closed == true` 的那
一則，這在 lib.rs 最上面的文件註解和 `KlineUpdate::bar` 的欄位註解都寫明了。測試
`parses_an_unclosed_kline_and_marks_it_not_closed` / `parses_a_closed_kline_and_marks_it_closed`
/ `open_and_closed_updates_for_the_same_bar_share_open_time` 三個一起確認：兩種狀態都能正確
解析、旗標對不對、而且同一根的 `open_time` 真的一致（呼叫端才可能把它們對成同一根）。

24hr ticker 串流（`e: "24hrTicker"`）簡單很多，最新成交價在 `c` 欄位。

### 重連策略：`Backoff`，時間當參數

失敗一次等 1 秒，之後每次翻倍、封頂 30 秒；只要成功連上一次（TLS handshake 過）就重置回
1 秒，不管這次連線後來活多久。`Backoff` 這個型別完全不知道「現在幾點」，只管「等多久」——
延續 4.3 帳戶費率同步「把時間當參數」的技巧，只是這裡參數化的是「等待時長」而不是「時間
戳」。測試不需要真的 `sleep`：

```rust
fn failure_delay(&mut self) -> Duration { /* 純函式，doubling + cap */ }
fn reset(&mut self) { self.current = None; }
```

連線迴圈本體 `run_with` 把「怎麼連線」和「怎麼睡」都變成參數（`impl FnMut`），測試用假的
`connect`／`sleep` closure，完全不連網路、不真的等待，毫秒內跑完整條「失敗兩次退避、第三次
成功收到訊息、斷線後退避重置」的路徑（見下方測試輸出）。

### 解析失敗、連線失敗都不會讓背景執行緒崩潰

- **訊息解析失敗**（JSON 壞掉、欄位對不上、數字格式不對、`Bar::validate()` 不通過）：
  `parse_event` 回傳 `None`，那一則訊息被安靜跳過，連線不受影響——下一則訊息一兩秒後就會
  再來。這條串流只有 ticker/kline 兩種事件類型，真的解析不了幾乎只會是 Binance 換了欄位
  格式，屬於之後要重新查證的情況，不是背景執行緒此刻能做什麼的情況。
- **連線失敗 / 讀取失敗 / 對方關閉連線**：`StreamError` 三種變體都只是「觸發重連」的訊號，
  不會 `unwrap`/`panic`，走 `Backoff` 退避後重試。

`run_with` 整個函式沒有任何 `unwrap`/`expect`/`panic!`。

### 呼叫端怎麼「停止」這條背景執行緒

`run_with` 的迴圈只有一個出口：往 channel 送事件時發現 `Receiver`已經被 drop
（呼叫端把整個 `MarketStreamHandle` 丟掉）。

ponytail：如果呼叫端在連線剛好斷線、正在退避等待的當下把 `MarketStreamHandle` drop
掉，背景執行緒不會立刻停止，要等下一次成功連線、真的送出下一則事件才會發現沒人收了。這條
串流不碰下單、沒有資源競爭風險，多跑幾秒不影響行為正確性。真的需要「立刻停止」（例如切換
交易對要馬上斷開舊連線）時，再加一個 `AtomicBool` 在迴圈開頭檢查——這一步不需要，因為還
沒有 UI 呼叫它。

```
running 11 tests
test tests::connects_to_real_binance_ticker_stream ... ignored
test tests::backoff_doubles_up_to_the_cap ... ok
```

分三類：

1. **訊息解析**：用官方文件格式、欄位補齊的真實 kline/ticker JSON 片段（含一堆這裡用不到的
   欄位，例如 `n`、`q`、`V`，確認多餘欄位不會讓解析失敗）。涵蓋收盤／未收盤、正常價格、
   壞掉的數字、驗證失敗的 K 線（最高價比開盤價低）。
2. **`Backoff`**：純函式邏輯，doubling、封頂、reset 後重新開始。
3. **`run_with` 連線迴圈**：假的 `connect`／`sleep`，驗證「失敗兩次各等 1 秒、2 秒 → 第三次
   成功收到一則 ticker 事件 → 斷線後退避重置回 1 秒」整條路徑，一次測試涵蓋了退避序列和
   「成功後重置」兩件事。

### 確認測試不是虛的：故意改壞兩個地方

| 故意改壞的地方 | 哪個測試抓到 |
|---|---|
| `is_closed` 寫死 `true`，不管 `raw.k.x` | `parses_an_unclosed_kline_and_marks_it_not_closed` |
| `Backoff::failure_delay` 拿掉 `.min(self.max)` 封頂 | `backoff_doubles_up_to_the_cap` |

兩處改完都還原了，`diff` 確認過和原檔完全一致。

## 建議閱讀順序

1. lib.rs 最上面的文件註解：同步設計的取捨、收盤／未收盤的語意，一次講清楚兩個最重要的
   設計決定。
2. `parse_event` / `kline_event` / `ticker_event`：Binance 原始 JSON 怎麼變成
   `MarketEvent`，以及為什麼解析失敗一律回傳 `None`。
3. `Backoff`：只有 20 行,但這是「時間當參數」技巧的第二個範例（第一個是 4.3）。
4. `run_with`：整個連線生命週期的骨架，`connect`／`sleep` 兩個參數是它可以被完整測試、
   不用連真實網路的原因。
5. `ensure_crypto_provider`：一個踩過的真實的坑，值得記住這個模式（多個 crate 都用 rustls
   時，process 級的 provider 需要手動裝一次）。

## 第 4 節（Binance 唯讀連線）全貌回顧

4.1（Keychain）→ 4.2（簽名 REST client）→ 4.3（費率同步）／4.4（下單規則同步，兩者共用
`at-account-sync` 的「24 小時快取、失敗沿用舊值」骨架）→ 4.5（這一步，公開 WebSocket 行情）
→ 4.6（連線設定畫面，只依賴 4.1，提前完成）。到這裡，回測引擎需要的三種外部資料——歷史
K 線（1.7）、帳戶費率／下單規則（4.3/4.4）、即時行情（4.5）——都有真實資料來源了，且全部
是唯讀、不會送出任何訂單。

對 ROADMAP 第 5 步（模擬交易：即時行情、模擬成交、按停止才結束）可以直接重用的部分：

- **`at-market-stream::spawn`／`MarketEvent` 本身**：模擬交易需要的「持續收到即時價格」這件
  事，這一步已經做完，第 5 步不用再處理 WebSocket、重連、收盤判斷這些細節，直接消費
  `handle.events` 就有資料。
- **「收盤 K 線才能用」這個判斷**：第 5 步如果要在收盤時觸發策略的 `on_bar`（2.1 的策略介面
  假設收到的都是已收盤的 K 線），`KlineUpdate::is_closed` 就是那個判斷點——用未收盤的 K 線
  呼叫 `on_bar` 會讓策略看到「還沒定案」的資料，這是這一步刻意查證、寫進文件的陷阱，第 5 步
  不會重踩。
- **成交模擬（2.3）與手續費滑價（2.4）的邏輯本身完全不用重寫**：那兩步已經是「收到一根收盤
  K 線 → 決定要不要成交」的形狀，第 5 步只是把「歷史 K 線」的來源換成「4.5 的即時收盤 K
  線」，中間的判斷邏輯是同一套。
- **`Backoff` 這個型別**：如果第 5 步還需要別的長連線（例如之後接使用者資料的 WebSocket 顯示
  訂單狀態），這個退避邏輯可以直接搬過去用，不用重寫。
