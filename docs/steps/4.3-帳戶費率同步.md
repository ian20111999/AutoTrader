# 4.3 帳戶實際費率同步

把 1.4 的 `FeeSchedule` 從「寫死的 VIP 0 預設值」換成「你帳戶的真實費率」：24 小時打一次
Binance，存到本機，打不通就沿用上次的值並標記成過期。這一步只打唯讀端點
`GET /api/v3/account/commission`，沒有任何送出訂單的程式碼路徑。

## 做了什麼

新增一個 crate：

- `crates/account-sync/Cargo.toml`（package 名稱 `at-account-sync`）：依賴 `at-binance`
  （4.2 的簽名 client）、`at-core`（1.4 的 `FeeSchedule`）、`serde` + `serde_json`。
- `crates/account-sync/src/lib.rs`：
  - `sync_spot_fees(base_dir, symbol) -> Result<SyncedFees, FeeSyncError>`：整條同步流程。
  - `SyncedFees { schedule, freshness }`：費率本身 + 這份資料新不新鮮。
  - `Freshness::Fresh` / `Freshness::Stale { age_ms }`。
  - `FeeSyncError::NoCachedFees` / `BadResponse` / `SystemClock`。
  - `cache_path(base_dir, symbol)`：`<base_dir>/fee_schedule_<SYMBOL>.json`。
  - `CACHE_TTL_MS`：24 小時。
- 根目錄 `Cargo.toml`：`members` 加上 `crates/account-sync`。

用起來像這樣：

```rust
let symbol = Symbol::new("BTCUSDT")?;
let synced = at_account_sync::sync_spot_fees("data", &symbol)?;
match synced.freshness {
    Freshness::Fresh => { /* 24 小時內同步成功的費率，可以直接用 */ }
    Freshness::Stale { age_ms } => { /* 提醒使用者：這是 age_ms 毫秒前的舊費率 */ }
}
let fee = synced.schedule.fee(&symbol, Liquidity::Taker, Side::Buy, price, qty)?;
```

## 為什麼這樣設計

### 為什麼是新的 crate，不是塞進 `at-core` 或 `at-binance`

- **不能放 `at-core`**：`at-core` 目前是零外部依賴（`Cargo.toml` 的 `[dependencies]` 是空的），
  這是它能被回測、模擬、實盤、桌面 App 到處重用的原因。這一步需要 `serde_json` 和檔案 I/O，
  放進去就破壞了這個定位。
- **不放 `at-binance`**：4.2 那個 crate 的定位是「簽名 + 送出 HTTP」的傳輸層，它自己的
  模組說明就寫明「不解析各端點的回應結構」。這一步除了解析回應，還做了**本機快取**——
  一個 REST client 順便管檔案快取和領域型別，是兩件不同的事混在一起。
- **crate 名稱叫 `account-sync` 不是 `fee-sync`**：4.4（下單規則同步）是一模一樣的形狀
  （從 Binance 拿帳戶/交易所設定 → 存本機 → 失敗沿用舊值），放同一個 crate 就好，不必開
  第二個長得幾乎一樣的 crate。

### 回傳型別：為什麼不直接回 `FeeSchedule`

如果只回一個 `FeeSchedule`，呼叫端拿到的是一份「看起來很正常」的費率，分不出這是剛同步
到的還是三個月前的。費率算錯會直接讓回測與實盤的損益失真，所以「這份資料有多新」必須是
**回傳值的一部分、強迫呼叫端面對**，而不是藏在某個要自己去查的欄位裡：

```rust
pub struct SyncedFees {
    pub schedule: FeeSchedule,   // schedule.synced_at = 上次「成功」同步的時間
    pub freshness: Freshness,
}

pub enum Freshness {
    Fresh,                  // 24 小時內同步成功（剛打完 API，或用還沒過期的快取）
    Stale { age_ms: i64 },  // 這次 API 失敗，沿用舊值，而且這份值已經 age_ms 毫秒舊了
}
```

沒有動 1.4 的 `FeeSchedule`／`CommissionRates`／`FeeModel` 任何公開 API——
`FeeSchedule::synced_at` 這個欄位 1.4 本來就留好了，這一步只是第一次真的去填它。

### 三條行為規則

1. **24 小時快取**：本機存的值不滿 24 小時就直接用，連 API 都不打。除了少打網路、避免踩到
   Binance 的 rate limit，還有一個實際好處：打 API 的那段程式碼放在 closure 裡，快取還新的
   時候**連 Keychain 都不會去讀**，不會每次都可能跳出 macOS 的授權對話框。
2. **失敗沿用舊值**：API 失敗（沒網路、金鑰失效、Binance 維護）不讓整個流程掛掉，改用本機
   舊值，但一定標成 `Stale` 並附上多舊。寧可用舊值，也不能靜默假裝資料是新的。
3. **沒有舊值就誠實報錯**：第一次用又剛好失敗時沒東西可以沿用，回 `NoCachedFees`，訊息建議
   呼叫端先確認連線設定或暫時改用 1.4 的 `FeeModel::spot_vip0()`。

### `base_dir` 為什麼是參數，不是寫死的 `"data"`

一開始寫死成相對路徑 `data/fee_schedule_BTCUSDT.json`，實測打真實 API 之後發現檔案跑到
`crates/account-sync/data/`——因為 `cargo test` 的工作目錄是 crate 目錄，不是專案根目錄。
相對路徑會跟著行程的工作目錄跑，同一份快取在不同啟動方式（`cargo run`、Tauri App、雙擊
執行檔）下會存到不同地方，24 小時快取等於形同虛設。

改成跟 1.7 `at_downloader::local_path(base_dir, ...)` 同一個慣例：**由呼叫端決定 base_dir**。
桌面 App 傳 Tauri 的 `app_data_dir()`（`app/src-tauri/src/backtest.rs` 已經是這樣拿路徑的），
命令列傳 `"data"`。

一個交易對一個檔案，不是全部塞一個檔：這樣就不需要「這份快取存的是不是我要的交易對」這種
判斷，也不會兩個交易對互相覆蓋對方的快取、害彼此每次都重打 API。`Symbol` 只允許大寫英數字
（`at_core::Symbol::new` 保證），組不出跳出 `base_dir` 的路徑。

### 為什麼引入 `serde` / `serde_json`

Binance 的回應是巢狀 JSON（四層費率群組 + 折扣開關），手寫 JSON 解析器在「算錢」這條路上是
最糟的選擇。專案之前沒有 JSON 需求（1.5 是 CSV、1.7 是 ZIP）所以一直沒裝；這是第一個真的
需要 JSON 的步驟，`serde` + `serde_json` 是 Rust 生態系的事實標準，`serde_json` 同時解決
「解析回應」和「寫快取檔」兩件事，不需要再為快取另外設計一個自訂文字格式。

費率在 JSON 裡是字串（`"0.00100000"`），程式裡先收成 `String` 再自己 `parse` 成 `Fixed`：
`Fixed` 住在零依賴的 `at-core`，不能掛 serde 的 derive；而且收字串比較好回報「是哪一欄不是
合法數字」。

### BNB 抵扣：兩個開關都要開

Binance 的 `discount` 物件有 `enabledForAccount` 和 `enabledForSymbol` 兩個開關，程式裡用
`&&`——少判一個就會把費率算太低（以為有折扣但其實沒有），回測會比實際賺。

`discount: "0.75"` 的語意是「標準費率要**乘上**的倍數」（打 75 折、省 25%），和 1.4
`SpotFees::bnb_discount` 的定義一致。這點用真實帳戶驗證過：帳戶標準費率是 0.1%、BNB 抵扣
開著，同步回來算出的吃單費率是 **0.00075 = 0.1% × 0.75**，正好等於大家熟知的「BNB 折 25%」。
如果這個欄位其實是「折掉 75%」，費率會差三倍，這是這一步最值得盯的一個數字。

### `specialCommission` / `taxCommission` 可以不存在

這三組費率在型別上是 `Option`：Binance 的真實回應裡（見下面的快取檔內容）欄位齊全，但不同
帳戶等級不保證每組都給。缺了就當 0（= 不收這筆費用），而不是整份回應解析失敗。
`standardCommission` 沒給則是真的沒辦法算，直接報錯。

### ponytail：刻意沒做的事

- **快取寫入失敗直接吞掉**：費率這次已經拿到手、照樣回傳，寫不進去的代價只是下次要多打一次
  API；為了磁碟寫入失敗就讓整個同步失敗更糟。真的需要在畫面上提示再改成回傳錯誤。
- **`Stale` 沒有附上失敗原因**：目前只帶「多舊」。之後如果 UI 要顯示「同步失敗：金鑰已失效」
  再把原因加進去。
- **只做 BTCUSDT 一個交易對、只做現貨**：合約費率端點（`/fapi/...`）等真的要接合約帳戶再說。

## 測試怎麼做到不依賴真實時間與真實網路

公開的 `sync_spot_fees` 只是薄薄一層，真正的邏輯在 `sync_spot_fees_with`，它把「現在幾點」
和「怎麼打 API」都變成參數：

```rust
fn sync_spot_fees_with(
    symbol: &Symbol,
    cache_path: &Path,
    now_ms: i64,                                        // 假的「現在」
    fetch: impl FnOnce() -> Result<String, BinanceError>, // 假的 API
) -> Result<SyncedFees, FeeSyncError>
```

沒有為了注入假實作而定義 trait（只有一個實作的 interface 是多餘的抽象）——`now_ms` 傳一個
數字、`fetch` 傳一個 closure 就夠了。測試用 `Cell<bool>` 記錄 closure 有沒有被呼叫，就能直接
斷言「快取還新的時候**完全沒有**打 API」，而不是只看回傳值猜。

14 個測試全部不連網路、不看系統時鐘，毫秒內跑完：

### 確認測試不是虛的：故意改壞四個地方

綠燈的測試只證明「現在是綠的」，不證明「壞掉時會紅」。所以把四個關鍵判斷分別改壞，確認對應
的測試真的會失敗（改完都還原了）：

| 故意改壞的地方 | 哪個測試抓到 |
|---|---|
| 24 小時邊界 `age < TTL` 改成 `age <= TTL` | `cache_exactly_24h_old_is_refetched` |
| 退回舊值時把 `Stale` 改成 `Fresh`（謊報新鮮） | `api_failure_falls_back_to_the_cached_value...` |
| BNB 兩個開關 `&&` 改成 `\|\|` | `bnb_discount_needs_both_switches_on` |
| `taxCommission` 對到 `specialCommission` 欄位 | `official_example_maps_every_field_to_the_right_slot` |

四個都紅了才算數。

## 本機快取檔長什麼樣

`cache_path` 回傳 `<base_dir>/fee_schedule_BTCUSDT.json`。下面是**真實帳戶**同步回來的內容
（費率不是機密，檔案裡沒有任何金鑰）：

```json
{
  "syncedAtMs": 1790671497793,
  "commission": {
    "symbol": "BTCUSDT",
    "standardCommission": { "maker": "0.00100000", "taker": "0.00100000", "buyer": "0.00000000", "seller": "0.00000000" },
    "taxCommission":      { "maker": "0.00000000", "taker": "0.00000000", "buyer": "0.00000000", "seller": "0.00000000" },
    "specialCommission":  { "maker": "0.00000000", "taker": "0.00000000", "buyer": "0.00000000", "seller": "0.00000000" },
    "discount": { "enabledForAccount": true, "enabledForSymbol": true, "discount": "0.75000000" }
  }
}
```

`syncedAtMs` 是「上次**成功**從 Binance 拿到這份費率」的 UTC 毫秒，`Freshness` 就是拿它和
現在比出來的。round-trip 測試（`fetched_fees_round_trip_through_a_real_file`）確認存進去、
讀回來的費率完全一致，寫法沿用 1.6 `bar_store` 的風格。

## 建議閱讀順序

1. `crates/account-sync/src/lib.rs` 最上面的模組說明：三條行為規則。
2. `sync_spot_fees_with`：整條流程的骨架（快取 → 打 API → 失敗退回），14 個測試全部打在這裡。
3. `CommissionJson::to_fee_model`：Binance 的欄位怎麼對到 1.4 `SpotFees`，特別是 BNB 抵扣。
4. 測試模組：`fresh_cache_is_used_without_calling_the_api` 和
   `api_failure_falls_back_to_the_cached_value_and_says_how_old_it_is` 這兩個是這一步的重點。

## 動手試試看

1. 把 `CACHE_TTL_MS` 從 24 小時改成 1 毫秒，重跑 `cargo test -p at-account-sync`，看
   `fresh_cache_is_used_without_calling_the_api` 會不會失敗——確認快取真的是照這個常數在判斷，
   不是剛好都走同一條路。
2. 把 `to_fee_model` 裡的 `d.enabled_for_account && d.enabled_for_symbol` 改成 `||`，重跑測試，
   看 `bnb_discount_needs_both_switches_on` 會不會抓到（這就是上面那張表在做的事）。
3. 跑一次 `cargo test -p at-account-sync -- --ignored --nocapture`，看你自己帳戶的真實費率是
   多少；如果你有開 BNB 抵扣，吃單費率應該是 0.00075 而不是 0.001。
