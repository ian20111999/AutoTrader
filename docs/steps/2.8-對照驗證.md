# 2.8 對照驗證：用一份獨立重寫的回測檢查引擎

## 做了什麼

拿一段**真實**的 BTCUSDT 歷史資料，把整條鏈跑一遍——

```text
download_and_store_monthly_klines  →  read_bars_file  →  SmaCross  →  run_backtest  →  Metrics
   （1.7 下載器）                      （1.6 儲存）      （2.7 策略）   （2.2-2.5 引擎）  （2.6 指標）
```

——再和一份**完全獨立重寫**的 Python 回測逐格比對：每一根 K 線的權益（8 位小數
全等）、成交筆數、四個績效指標。比對寫成會跑的測試放進倉庫，不是一份「我比對過了」
的文件。

新增的檔案：

| 檔案 | 作用 |
|---|---|
| `docs/reference/manual_verification_sma_cross.py` | 獨立的第二套實作：只照規格從頭算 |
| `docs/reference/manual_verification_sma_cross.out.txt` | 上面那支腳本的輸出（逐根均線、訊號、成交、權益、指標） |
| `crates/downloader/tests/integration_sma_cross_validation.rs` | 整合測試：把 Python 的答案寫成斷言 |
| `crates/downloader/tests/fixtures/BTCUSDT/1d/BTCUSDT-1d-2024-01.csv` | 對照用的真實資料，31 根日線 |

## 一開始就要講清楚：原本的驗收標準做不到

ROADMAP 原本寫「和之前 Python 回測結果比對」，指的是另一台機器上舊的一份 Python
回測（12 組標準答案）。**那份資料不在這個 repo 裡，也沒有被帶過來**，所以不可能
拿它來比。這一步只能改成「自己再寫一套獨立的實作來對照」。

兩者的差別要老實說：

- 原本的計畫是**外部黃金標準**——一份先存在、和 Rust 引擎毫無關係的答案。
- 現在做的是**獨立重新推導**——同一個人照同一份規格寫第二套實作。它抓得到
  「規格理解錯」「算式寫錯」「差一根」這類錯，但抓不到「規格本身就錯」。

**如果之後找到或補得出那份原始 Python 回測，這一步應該重做一次**：資料換成
那 12 組、驗收標準回到原本的「交易次數完全一致、報酬／回撤／夏普誤差 < 1e-6」。
現在這份測試不會因此作廢，它會變成「便宜的迴歸測試」，原始對照才是「嚴格驗收」。

## 獨立性做到哪裡（誠實揭露）

寫 Python 那支腳本時**沒有讀** `backtest.rs`、`metrics.rs`、`strategies/sma_cross.rs`
的實作內容。依據的只有：

1. `CLAUDE.md`：「訊號在 K 線收盤產生，下一根開盤成交；手續費依帳戶實際費率；
   滑價、資金費分開記帳」。
2. `docs/ROADMAP.md` 2.6 那一行括號：夏普取樣頻率跟著 K 線週期、年化用時間戳算、
   一年 365 天、無風險利率 0、標準差用母體（除以 n）。
3. `strategy.rs` 的介面文件：目標部位是**資金比例**（0 空手、1 滿倉做多、負數做空），
   暖機不足回空手。
4. `SmaCross` 的行為宣告（型別上方的文件，不是 `on_bar` 的程式碼）：兩條 SMA 都用
   收盤價；快線 > 慢線滿倉做多，其餘（含相等、暖機不足）空手；暖機 = 慢線週期。
5. `Fixed` 的算術契約（1.1）：8 位小數，乘除在第 9 位四捨五入（0.5 遠離零）。
6. `FeeModel::fee` 的定義：手續費 = 價格 × 數量 × 費率，以報價幣計；
   `FeeModel::spot_vip0()` 是掛單／吃單都 0.1%。

也**看了**這些，因為不看就沒辦法呼叫引擎：`BacktestConfig` 的欄位名稱與單位
（例如「滑價 0.0005 就是 0.05%」）、`run_backtest` 與 `Metrics::from_curve` 的簽名、
儲存檔的欄位順序。這些是介面契約，不是算法。

**唯一一次事後讀實作**是在診斷夏普的最後幾位差異時（見下面「差異診斷」）。
那時候權益曲線與其他三個指標已經比對完成，不影響前面的獨立性。

## 選什麼資料、什麼策略、為什麼

- **資料：BTCUSDT 2024-01 日線，31 根。** 日線資料量小，可以整份印出來人眼核對；
  2024 年 1 月的 BTC 先漲到 48969 再跌到 38555，有漲有跌也有一次明顯的趨勢反轉，
  不是一條單調的線（單調資料會讓「差一根」的錯藏起來）。
- **策略：`SmaCross(fast=3, slow=8)`。** 均線交叉最直觀，可以手算；週期選小的，
  31 根資料才會出現多次交叉（實際出現 3 筆成交：進場、出場、再進場）。
  預設的 (10, 50) 在 31 根資料上永遠暖機不足，一筆都不會成交，驗不到東西。
- **起始資金 10000 USDT**，兩個情境：零成本，以及滑價 0.05% + 現貨 VIP0 吃單費 0.1%。

## 差異診斷

### 夏普差 10⁻⁶ 量級：精度，不是公式

第一次跑，除了夏普全部對上。差 1.7×10⁻⁶ 看起來很小，但**不能就這樣放過**——
夏普算錯最常見的兩種原因（標準差用樣本而不是母體、每年期數寫死 365）都會造成
10⁻² 以上的差，10⁻⁶ 雖然不像公式錯，還是得說出它從哪裡來。

先排除幾個假設（Python 端改一個變因就重算一次）：

| 假設 | 算出來 | 對得上 −3.14010028？ |
|---|---|---|
| 報酬全程用 f64 | −3.14010202 | 否，差 1.7×10⁻⁶ |
| 報酬先量化成 8 位小數 | −3.14010185 | 否 |
| 標準差用樣本（除以 n−1） | −3.08732343 | 否，差 5×10⁻² |

都不對，所以去讀了 `metrics.rs`（此時其他項目已經比對完）。原因是引擎
**連開根號都用整數算**，為的是「同一份輸入永遠得到同一個數字」：

- 平均值是 i128 的**截尾**除法，不是四捨五入；
- 標準差用 `isqrt`，取 **floor**，不四捨五入；
- 每年期數 = 報酬個數 ÷ 年數（都是 8 位小數的定點數），不是 `一年毫秒數 ÷ K線毫秒數`。
  兩者數學上等價，數值上差一點（算出來是 365.00000365 而不是 365）。

照這條全整數路徑在 Python 裡重算一次（`sharpe_all_integer()`），得到
**−3.14010028，和引擎一位不差**。含成本的情境也一樣（−3.31327177）。
到這裡診斷結束：兩套實作的**方法論一致**，差的是量化誤差。

年化報酬的 4×10⁻⁸ 同理：引擎的小數次方是用「連續開根號」展開的，
`metrics.rs` 自己就寫了「累積誤差量級約 10⁻⁷，最後一兩位是雜訊」。

因此測試對總報酬、最大回撤、期間、**每一點權益**要求 8 位小數完全相等，
只對年化與夏普給 2×10⁻⁵ 的容許誤差，並在測試裡寫清楚為什麼這個門檻仍然嚴格。

### 兩個規格沒寫清楚、靠比對才發現的行為

這是這次對照最有價值的產出——不是「抓到 bug」，而是**問出兩個規格沒回答的問題**。
第一次推導時我對兩個問題各猜了一種答案，其中一個猜錯：

**1. 目標部位沒變時，要不要每根重新平衡？（我猜錯了）**

我一開始讓 Python 每根都重算「權益 ÷ 價格」。零成本時這沒差別（滿倉時
權益 ÷ 開盤價剛好等於手上的數量）。但含滑價時，買價比開盤價貴 0.05%，
每根重算就會賣掉一小片碎屑：

```text
第  9 根 賣出 數量 0.00032316 手續費 0.01489346
第 10 根 賣出 數量 0.00000171 手續費 0.00007974
第 11 根 買進 數量 0.00000072 手續費 0.00003338
...
```

10 筆成交、白付 0.045 USDT。引擎**只在目標部位改變時才調倉**（3 筆），這是對的：
`TargetPosition` 是「我想要多少」，規格沒有要求把它當成需要持續追蹤的再平衡目標。
Python 端改成同一個慣例後才對得上。這件事值得寫進規格：
**目標部位不變 = 不下單**，未來加「偏離多少才再平衡」的參數時要明確設計。

**2. 含手續費時，部位要不要預留手續費？（我猜對了）**

如果數量 = 權益 ÷ 買價，那手續費就沒錢付了，現金會變成負的。所以合理的做法是
數量 = 權益 ÷ (買價 × (1 + 費率))，把手續費先留下來。Python 兩種都算了
（`.out.txt` 的情境 B 與 B'），引擎和「預留手續費」那一版完全一致。
這個規則目前只存在於程式碼裡，規格沒寫。

**沒有發現任何 bug。** 引擎在成交時點、成交價、數量、手續費、滑價、權益記帳、
四個指標上都和獨立推導一致。

## 怎麼驗證

```bash
# 1. 三道關卡
cargo fmt --all
cargo clippy --all-targets -- -D warnings
cargo test

# 2. 只跑這一步的對照驗證
cargo test -p at-downloader --test integration_sma_cross_validation

# 3. 連網重跑整條鏈（重新下載，確認和倉庫裡的樣本逐根相同）
cargo test -p at-downloader --test integration_sma_cross_validation -- --ignored

# 4. 重跑獨立的 Python 推導，自己看逐根的均線、訊號、成交、權益
python3 docs/reference/manual_verification_sma_cross.py
```

測試裡有四個：

| 測試 | 驗什麼 |
|---|---|
| `frictionless_backtest_matches_independent_derivation` | 零成本：31 點權益 + 成交筆數 + 四個指標 |
| `backtest_with_fees_and_slippage_matches_independent_derivation` | 含滑價與手續費：同上 |
| `costs_can_only_make_the_result_worse` | 方向性健全檢查：加了成本不可能變賺 |
| `downloaded_data_reproduces_the_fixture_and_the_derivation`（`#[ignore]`） | 連網：重新下載 → 存檔 → 讀回，逐根相同，再跑完整比對 |

主測試不碰網路（CI 不該因為別人的網站掛掉而變紅），連網那個要 `--ignored` 才跑。

### 突變測試：確認這些測試真的抓得到錯

把 `FAST` 從 3 改成 5 再跑，兩個比對測試都紅：

```text
test frictionless_backtest_matches_independent_derivation ... FAILED
assertion `left == right` failed: 1706400000000 的權益
```

順手發現一件事：改成 4 **不會**紅——在這 31 根資料上，SMA(3) 與 SMA(4) 和 SMA(8)
的交叉點剛好一模一樣（Python 端也算出同樣的結果，所以是資料的巧合，不是測試失靈）。
這正好提醒：驗證要用「會改變結果」的突變，不能假設任何參數變動都一定造成差異。

## 建議閱讀順序

1. `docs/reference/manual_verification_sma_cross.out.txt` 的情境 A ——
   先看那張逐根表格：收盤價、SMA(3)、SMA(8)、訊號、權益。看懂「第 7 根
   快線 44949 > 慢線 44389 → 出多單訊號，第 8 根開盤 46951.04 成交」，
   就懂了整個回測最重要的一件事：**訊號在收盤產生、下一根開盤成交**。
2. `docs/reference/manual_verification_sma_cross.py` 的 `backtest()` ——
   30 行，一根 K 線做三件事：開盤調倉、收盤標記權益、餵給策略拿下一個目標。
3. 同一支腳本的 `metrics()` —— 四個指標的算式攤開來，和 2.6 的說明對著看。
4. `crates/downloader/tests/integration_sma_cross_validation.rs` ——
   看那兩張 31 點的常數表怎麼變成斷言。
5. 回頭看本文「兩個規格沒寫清楚」那一節。

## 動手試試看

1. **改參數，兩邊一起改。** 把 Python 的 `FAST, SLOW = 3, 8` 改成 `2, 8`，
   重跑腳本，再把測試裡的兩張常數表換成新的輸出。對得上，就是自己也做了一次對照驗證。
2. **換一個月。** 把 `MONTH` 改成 3（2024 年 3 月 BTC 創了新高，是明顯的上升趨勢），
   跑 `--ignored` 那個測試抓資料，再跑 Python，看趨勢明確的月份裡均線交叉賺不賺錢。
3. **把成本調誇張。** 滑價改成 1%（`0.01`），看 3 筆成交吃掉多少報酬。
   這是為什麼 `frictionless` 的文件寫著「不要拿它評估策略好不好」。
4. **故意做錯一件事。** 把 Python 的成交價從「下一根開盤」改成「這一根收盤」
   （`bar.open` 換成 `bar.close`），看期末權益差多少。那個差額就是
   「用未來的價格成交」這種常見錯誤能虛構出多少報酬。
5. **驗一下夏普的取樣頻率。** 把腳本裡的 `periods_per_year` 寫死成 365
   去算一份 1 小時 K 線的夏普，和正確的 8760 比——差 4.9 倍，
   這是 2.6 說「這個指標最常見的錯」的實際大小。

## 還沒做的事

  以及做空／槓桿／資金費（2.5）都還沒有獨立對照——它們有單元測試，但沒有第二套
  實作驗算過。
- 沒有比對原始的 Python 黃金標準（不存在）。**找到就重做這一步。**
- 資金費與強制平倉的對照需要合約資料（U 本位的 `data.binance.vision` 路徑和現貨
  不同，1.7 的下載器目前只組現貨路徑），留到需要的時候再做。
