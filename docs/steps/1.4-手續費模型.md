# 1.4 手續費模型 `FeeModel`、`FeeSchedule`

## 做了什麼

新增 `crates/core/src/fees.rs`：

- **`CommissionRates`**：一組費率，欄位和 Binance 現貨 API 一樣：`maker`、`taker`、`buyer`、`seller`。
- **`FeeModel`**：一個交易對的費率模型，分現貨 `Spot` 和合約 `Futures` 兩種。
  - `rate(掛單或吃單, 買或賣)`：這筆成交實際適用的費率（已含 BNB 折扣）。
  - `fee(掛單或吃單, 買或賣, 價格, 數量)`：這筆成交要付多少手續費。
  - `spot_vip0()`、`futures_vip0()`：Binance 公開的最低等級費率，還沒抓到帳戶費率前當預設值。
- **`FeeSchedule`**：整個帳戶的費率表，每個交易對一個模型，並記錄最後同步時間 `synced_at`。

## 費率怎麼算

**現貨**：三組費率相加才是實際付的錢。

```
費率 = 標準 × BNB 折扣 + 稅費 + 特殊
其中每一組 = 掛單或吃單費率 + 買方或賣方費率
```

- BNB 折扣只折「標準」那部分，稅費和特殊費率不折。Binance 回傳 `discount: 0.75` 表示打 75 折，VIP 0 的 0.1% 就變成 0.075%。
- 大部分帳戶的稅費、特殊、買方、賣方費率都是 0。

**合約**：每個交易對有自己的掛單、吃單費率。開 BNB 抵扣時整個手續費乘上折扣倍數。
合約的 API 只告訴你「有沒有開」，不給折扣比例，所以倍數由之後的程式依 Binance 公告填入。

**手續費** = 成交金額（價格 × 數量）× 費率，四捨五入到小數第 8 位。

## 幾個設計決定

- **找不到交易對就報錯，不當成 0**：少算手續費會讓回測看起來比實際賺，這種錯最危險，所以寧可停下來。
- **費率可以是負數**：高等級帳戶的合約掛單可能有返佣，這時手續費是負的（你收錢）。
- **手續費以 USDT 計**：開 BNB 抵扣時實際扣的是 BNB，這裡記它等值多少 USDT，方便和損益放在一起看。
- **這一步不連線 Binance**：費率怎麼從帳戶抓是第 4 步的事。這一步只負責「拿到費率之後怎麼算」，所以可以完全用測試驗證。
- **回測、模擬、測試網、實盤共用這一份**：成本算法只寫一次，四種模式不會算出不同的數字。

## 怎麼驗證

```bash
cargo test -p at-core fees
```

應該看到 11 個 `fees::tests::...` 全部 `ok`。全部測試 `cargo test` 共 53 個。

## 建議閱讀順序

1. `fees.rs` 最上面的說明：費率從哪兩個 API 來
2. 測試 `spot_vip0_costs_one_usdt_per_thousand`、`bnb_discount_only_applies_to_standard_part`
3. `FeeModel::rate`：現貨和合約的算法差在哪
4. `FeeSchedule::fee`：為什麼找不到交易對要報錯

## 動手試試看

1. 在 `bnb_discount_only_applies_to_standard_part` 裡，把稅費從 `"0.0001"` 改成 `"0"`，先猜期望值應該改成多少，再跑測試驗證。
2. 把 `FeeSchedule::fee` 改成找不到交易對時回傳 `Ok(Fixed::ZERO)`，跑測試看哪一個測試抓到這個「少算手續費」的錯誤，再改回來。
