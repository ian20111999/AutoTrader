# 5.3 執行生命週期：按停止就停止，隨時查得到目前狀態

5.2 把行情接上引擎之後，模擬交易只有「開始」沒有「停止」：要停只能把 `PaperTradingHandle`
丟掉，而且底層的 WebSocket 執行緒（4.5）根本沒有任何停止機制——4.5 的註解明白寫著「之後有 UI
要呼叫時再加 `AtomicBool`」。這一步就是把那個伏筆補上，並且讓畫面隨時問得到「現在手上有多少倉、
權益多少」。

這一步依然沒有任何送出訂單的程式碼路徑。

## 做了什麼

### 一、`PaperTradingHandle` 多了兩個方法

```rust
impl PaperTradingHandle {
    /// 要求停止：模擬交易迴圈和底層的行情連線都會結束。
    pub fn stop(&self);

    /// 現在的部位與權益（最後一根收盤 K 線進帳本之後的完整狀態）；
    /// 還沒有任何一根收盤 K 線進帳本時回 None。
    pub fn latest_snapshot(&self) -> Option<PaperSnapshot>;
}
```

`PaperUpdate` 多了一個變體：

```rust
pub enum PaperUpdate {
    Bar(PaperSnapshot),
    Stopped,              // ← 新增：使用者主動停止，帳本完整
    Failed(BacktestError),
}
```

`Stopped` 和 `Failed` 是完全不同的兩件事，畫面要分開處理：

| 更新 | 帳本 | 畫面該怎麼做 |
|---|---|---|
| `Stopped` | **完整**，只是不再更新 | 顯示「已停止」，曲線留著給使用者看 |
| `Failed(e)` | **不完整**，從那根起不可信 | 顯示錯誤，告訴使用者數字不能用 |

### 二、`MarketStreamHandle` 終於能停了

```rust
impl MarketStreamHandle {
    /// 要求背景執行緒收工：關掉連線、結束重連迴圈。
    pub fn stop(&self);

    /// 把同一個停止旗標交給上層（5.3 的 at-paper-trading）。
    pub fn stop_flag(&self) -> Arc<AtomicBool>;
}
```

### 三、兩層是同一個開關

`at_paper_trading::spawn` 一開頭就做這件事：

```rust
let stop = stream.stop_flag();   // 拿到的是同一個 Arc，不是複本
```

所以 `PaperTradingHandle::stop()` 和 `MarketStreamHandle::stop()` 設定的是**同一個旗標**。
使用者按一次停止，模擬交易迴圈和 WebSocket 執行緒都會收工，不會留下一條還在收行情、還在
自動重連的孤兒連線。

## 難的地方：阻塞的讀取看不到旗標

旗標本身不難，難的是兩層都卡在「阻塞等待」裡：

| 層 | 原本卡在哪 | 卡多久 | 怎麼解 |
|---|---|---|---|
| 模擬交易迴圈 | `events.recv()` | 1 分鐘 K 線之間將近 60 秒沒有事件 | 換成 `recv_timeout(200ms)`，逾時就回頭看旗標 |
| WebSocket 讀取 | `socket.read()` | 無上限（安靜的串流可以好幾秒沒訊息） | 幫底層 TCP socket 設 500ms 讀取逾時 |
| 斷線退避等待 | `thread::sleep(delay)` | 最久 30 秒（退避上限） | 切成 100ms 一段，每段之間看旗標 |

第三行很容易被忽略：如果連線剛好斷掉、正在等 30 秒才要重連，使用者按停止會等半分鐘才有反應。

### WebSocket 的讀取逾時是查證過的用法

`tungstenite` 沒有「read timeout」這種設定，但它的 `read()` 文件明講：`Error::Io` **除了
`WouldBlock` 之外**才算致命錯誤（<https://docs.rs/tungstenite/0.30.0/tungstenite/protocol/struct.WebSocket.html#method.read>，
原文 "consider these fatal except for WouldBlock"），而且它內部會把讀到一半的訊框留在自己的
緩衝區裡，下一次 `read()` 接著讀完。所以正確做法是往下一層設 TCP 的逾時，把逾時當成「現在還
沒有新訊息」：

```rust
let tcp = match socket.get_mut() {
    MaybeTlsStream::Plain(tcp) => tcp,
    MaybeTlsStream::Rustls(tls) => &mut tls.sock,   // 穿過 rustls 拿到真正的 socket
    _ => return Err(/* ... */),
};
tcp.set_read_timeout(Some(READ_TIMEOUT))?;
```

`MessageSource::read_message` 的回傳型別因此從 `Result<String, _>` 變成
`Result<Option<String>, _>`：`Ok(None)` = 逾時（連線還好著），`Err` = 真的斷線要重連。
把逾時誤判成斷線的後果很具體——每 500ms 重連一次，等於自己對 Binance 發動連線風暴。

逾時在 Unix 上是 `WouldBlock`、Windows 上是 `TimedOut`，兩個都要認。TLS 那層不需要特別處理：
逾時打斷半個 TLS record 時，rustls 會把它留在自己的緩衝區，下一次讀取接著讀（這也是實機驗證
過的，見下面）。

沒有為了停止機制引入 `tokio`，4.5 的同步 + 背景執行緒架構完全沒動；連線、解析、重連的邏輯本體
一行都沒改。

## 為什麼「目前狀態」要另外存一份

`updates` 這條 channel 是**事件流**：每根收盤 K 線一則，要逐則消費才不會漏掉曲線上的點。
但畫面還需要另一種查詢：「現在權益多少、手上有多少倉」——使用者切走又切回來、視窗重畫、
剛打開頁面，這些時候不可能把整條 channel 重播一次。

所以背景執行緒每次成功 `on_bar` 之後多做一件事：把同一份 `PaperSnapshot` 寫進一個
`Arc<Mutex<Option<PaperSnapshot>>>`，`latest_snapshot()` 直接讀它。兩者互補：

- 曲線 ← 事件流（`updates`），不能漏。
- 部位／權益數字 ← 目前狀態（`latest_snapshot()`），只要最新的。

順序刻意是「先寫目前狀態，再送事件」：消費端收到 `Bar` 之後馬上問 `latest_snapshot()`，
看到的一定是這一根、不會是上一根。

還沒有任何一根收盤 K 線進帳本時回 `None`，而不是「權益 = 起始資金」——後者是猜的，第一個
權益點要等引擎真的算過才算數。

`PaperSnapshot` 本身沒有加任何欄位：它的 `point.equity` 就是總權益，`cash`/`position` 就是
目前部位，ROADMAP 5.3 要的「查詢目前部位與權益」已經齊了。`PaperEngine`（5.1）的公開介面
這一步一行都沒改。

## 不 panic

- `Mutex` 被下毒（曾經有執行緒持有鎖時 panic）時，讀的那邊回 `None`、寫的那邊放棄更新，
  兩邊都不 `unwrap`。事件流本身不受影響。
- 停止時送 `Stopped` 用的是 `let _ = send(...)`：消費端可能已經走了，送不出去也一樣要停。

## 怎麼驗證

```bash
# 1. 三道關卡
cargo fmt --all
cargo clippy --all-targets -- -D warnings
cargo test

# 2. 這一步的兩個 crate
cargo test -p at-paper-trading
cargo test -p at-market-stream

# 3. 真的連 Binance 跑一遍（需要網路）
cargo test -p at-paper-trading -- --ignored --nocapture
cargo test -p at-market-stream -- --ignored --nocapture
```

第 3 條在實機上的輸出（2026-09-30）：

```
收到真實收盤 K 線的模擬交易更新：時間 1790754480000、權益 10000、現金 10000、部位 0
按下停止到模擬交易迴圈結束：206.906625ms
test tests::runs_against_the_real_binance_kline_stream ... ok

收到即時價格：BTCUSDT = 83409.99
呼叫 stop() 到真實連線的背景執行緒結束：502.45375ms
test tests::stop_ends_a_real_binance_connection ... ok
```

502ms 正好是一次 `READ_TIMEOUT`，這證明兩件事：讀取逾時真的生效（TLS 那層沒有把它吃掉），
而且旗標一設就在下一次逾時被看到。

這一步新增的測試各自釘住一件事：

| 測試 | 釘住什麼 |
|---|---|
| `stop_ends_the_loop_and_says_so`（paper） | 行情 channel 一直開著但沒有事件時迴圈不會自己結束；`stop()` 之後收到 `Stopped`，而且那是最後一則（接著是 `Disconnected`，代表執行緒真的結束了） |
| `stopping_the_paper_loop_raises_the_shared_market_stream_flag`（paper） | 模擬交易的 `stop()` 設定的就是行情連線那一層的旗標——兩層連動是型別層面保證的，不是靠兩次呼叫 |
| `a_fresh_handle_has_no_current_state`（paper） | 還沒餵過任何 K 線時 `latest_snapshot()` 回 `None` |
| `latest_snapshot_matches_the_last_bar_update`（paper） | 餵三根有漲有跌的收盤 K 線（滿倉做多，權益和部位每根都在動），`latest_snapshot()` 和最後一則 `Bar` 更新完全相等 |
| `same_bars_give_the_same_numbers_as_a_backtest`（paper，5.2 就有） | 多了一條斷言：跑完之後的「目前狀態」就是最後一則 `Bar`，不是另外算的一份 |
| `stop_ends_the_background_loop_without_waiting_for_a_message`（stream） | 假來源每次讀取都逾時（永遠安靜的串流）：50ms 內迴圈不會自己結束，`stop()` 之後執行緒結束（用「sender 被 drop → 主執行緒收到 `Disconnected`」當證據，不需要 join 超時機制） |
| `a_read_timeout_is_not_treated_as_a_disconnect`（stream） | 來源連兩次逾時再吐一則 ticker：那則 ticker 照樣送出，而且整段只退避一次——逾時不可以觸發重連 |
| `a_backoff_wait_returns_immediately_once_stopped`（stream） | 旗標已設定時，30 秒的退避等待立刻回來（不會讓使用者等半分鐘） |

測試怎麼做到不連網路又跑得快：

- paper 這邊多了一個 `spawn_with(events, stop, ...)` 的內層函式，`spawn` 只是「從
  `MarketStreamHandle` 拿出 receiver 和旗標」的薄殼。測試塞一個普通的 `mpsc::channel` 進去，
  就能驗**真的** `PaperTradingHandle` 的每個方法。
- 「執行緒真的結束了嗎」不用 sleep 等，也不用 join 超時（std 沒有）：背景執行緒結束時它的
  sender 會被 drop，主執行緒的 `recv_timeout` 就會收到 `Disconnected`。
- 整包測試（8 + 13 個）跑完 0.27 秒。

另外做了突變測試（把程式改壞，確認測試真的會紅）：把 `run` 迴圈開頭的旗標檢查改成 `if false`
→ paper 的 `stop_ends_the_loop_and_says_so` 和 stream 的
`stop_ends_the_background_loop_without_waiting_for_a_message` 都失敗；把「寫入目前狀態」那行
拿掉 → `latest_snapshot_matches_the_last_bar_update` 和
`same_bars_give_the_same_numbers_as_a_backtest` 都失敗。

## 建議閱讀順序

1. `crates/paper-trading/src/lib.rs` 的 `PaperTradingHandle`：兩個新方法加起來不到十行。
2. 同檔的 `run`：四個出口都寫在文件註解裡；注意 `recv_timeout` 而不是 `recv`，以及「先寫
   目前狀態、再送事件」的順序。
3. `crates/market-stream/src/lib.rs` 的 `MessageSource` trait：回傳型別為什麼要多一層
   `Option`。
4. 同檔的 `set_read_timeout`：怎麼穿過 rustls 拿到底層 TCP socket。
5. 同檔的 `run_with` 與 `sleep_unless_stopped`：旗標在三個地方被看（迴圈外、讀取迴圈內、
   退避等待中）。

## 動手試試看

1. 把 `crates/market-stream` 的 `set_read_timeout(&mut socket, READ_TIMEOUT)?` 註解掉，跑
   `cargo test -p at-market-stream -- --ignored --nocapture`。真實連線那個停止測試會卡住直到
   Binance 下一則訊息才結束——正常時候看不出差別（每秒都有訊息），但這就是「停止會不會即時」
   的差別所在。
2. 把 `WsSource::read_message` 的 `Err(e) if is_read_timeout(&e) => return Ok(None)` 拿掉，
   跑 `cargo test -p at-market-stream`。`a_read_timeout_is_not_treated_as_a_disconnect` 會
   失敗；真實連線的話你會看到它每 500ms 重連一次。
3. 把 `run` 裡「先寫目前狀態、再送事件」的順序交換（先 `send` 再寫 `latest`），跑
   `cargo test -p at-paper-trading`。測試大多還是綠的——這是真實世界的競態：消費端收到 `Bar`
   之後馬上問 `latest_snapshot()`，偶爾會拿到上一根。順序是免費的保險。

## 還沒做的事

- **畫面（5.4）**。開始／停止按鈕、即時權益曲線、部位面板都還沒有；這一步只是把 UI 會呼叫的
  方法準備好。
- **停止之後不能「續跑」。** `stop()` 是單向的：旗標設下去就不能再開回來，要重新開始就再
  `spawn` 一次（引擎、策略狀態全部重來）。暫停／繼續是完全不同的需求，現在不需要。
- **斷線期間漏掉的 K 線還是不會補**（5.2 就列在這裡，這一步沒改變）。
- **`stop()` 之後行情 channel 裡可能還剩幾則事件沒消費完**，它們會跟著 receiver 一起被丟掉。
  這是對的：使用者按了停止就是不要再記帳了。
