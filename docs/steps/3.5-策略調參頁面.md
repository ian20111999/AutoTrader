# 3.5 策略調參頁面

## 做了什麼

新增 `app/src/StrategyParamForm.tsx`：一個依 `StrategyInfo.params` schema 動態產生欄位的參數表單，
不是為四個策略各寫一套表單。`Strategies.tsx` 現在有兩個畫面（同一個分頁內切換，不佔用 SideNav）：

- 列表畫面：3.4 的卡片格線，每張卡片新增一顆「調整參數」按鈕。
- 調參畫面：點「調整參數」後顯示，`<label>` 綁 `<input>`，錯誤訊息用 `aria-describedby` 關聯到對應欄位、
  `aria-invalid` 標記壞值欄位，「返回策略庫」／「套用參數」兩個動作。

套用參數後的結果（選了哪個策略＋每個欄位目前的值）存在 `App.tsx` 的 `strategyConfig` state
（型別 `StrategyConfig`，新增在 `strategyTypes.ts`），不是放在 `Strategies.tsx` 內部——因為 3.6 回測頁面
是同一層的另一個分頁（`{page === "backtest" && ...}`），兩個分頁是兄弟關係不是父子，狀態要放共同的上層
才能在切分頁之後還在。套用參數會同時把該策略標成選中狀態（3.4 就有的選中樣式），讓使用者一眼看出「現在
套用的是哪個策略」。

## 為什麼要這樣做

### 動態表單怎麼做到「不是四套硬編碼表單」

`StrategyParam` 只有 `key`/`label`/`kind`（integer/decimal）/`default` 四個欄位，`StrategyParamForm`
純粹用 `strategy.params.map(...)` 產生對應數量的 `<input>`，欄位的 `label`、`id`、`inputMode`
（integer 用 `numeric`、decimal 用 `decimal`）都從 schema 讀，不寫死任何策略特定的表單版面。
四個策略共用同一個元件、同一份渲染邏輯——差別只在傳進去的 `strategy` 物件不同。

### 驗證規則的取捨：型別驗證是通用的，語意驗證有少量策略特定規則

`kind` 只能表達「這是整數還是小數」，表達不出「這個小數欄位的合法範圍是多少」這種語意。
對照 `crates/core/src/strategies/mod.rs` 的 `StrategyParamError`：

| 規則 | 來源 | 這裡怎麼判斷 |
|---|---|---|
| 週期必須 > 0 | `ZeroPeriod` | **純看 `kind === "integer"`**：四個策略現有的整數欄位全部是「週期」，這條規則不用知道是哪個策略 |
| 快線週期 < 慢線週期 | `FastNotBelowSlow` | 只有 `sma_cross` 有這個欄位組合，用 `strategy.id === "sma_cross"` 判斷 |
| 標準差倍數必須 > 0 | `NonPositiveMultiplier` | 只有 `bollinger` 的 `multiplier` 欄位，用 `strategy.id === "bollinger"` 判斷 |
| RSI 門檻在 0～100 之間 | `ThresholdOutOfRange` | 只有 `rsi` 的 `buyBelow`/`exitAbove`，用 `strategy.id === "rsi"` 判斷 |
| RSI 進場門檻 < 出場門檻 | `ThresholdsOutOfOrder` | 同上 |

前四個策略的整數欄位剛好全部是「週期」語意一致，所以型別驗證可以完全通用；但小數欄位（倍數 vs. 門檻）
語意不同，`StrategyParam` schema 現在的形狀表達不出這個差異，只能用 `strategy.id`/`param.key`
做少量對照——這不是「四套硬編碼表單」（表單的渲染邏輯、欄位產生、輸入框樣式都是同一份），
只是驗證規則的最後一小塊要對照 Rust 端已經寫好的語意。錯誤訊息文字直接照抄
`StrategyParamError` 的 `Display`，跟 Rust 端保證一致。

驗證只在前端做，不會真的呼叫 Rust 端；3.6 執行回測時 Rust 建構子本來就會用同一組規則再驗證一次，
前端這層純粹是「先擋掉，讓使用者不用等回測才知道錯」。

### 設計稿砍到哪裡：3.5 / 3.6 範圍界線

設計稿 `StrategyEditor.dc.html` 是完整的視覺化策略建構器：左側可拖曳的指標積木（SMA/EMA/RSI/MACD/
布林通道...）、中間拖放式條件編輯器（AND/OR 群組、比較運算子、做多做空鏡像）、現貨/合約切換、槓桿與
保證金模式、停損設定、右側「即時預覽」K 線圖疊加進出場箭頭、快速回測結果卡（年化/回撤/近12個月）、
儲存版本與「執行回測」按鈕連去回測頁。

這個 App 現在只有 4 個內建策略的**固定參數**（`entry_period`/`multiplier` 這種數字），沒有條件建構器、
沒有指標積木、沒有 K 線資料可以畫即時預覽、不支援合約/槓桿/停損設定（那是 2.5 已經做在 Rust 引擎裡但
還沒有桌面介面的部分）、也還沒有「執行回測」的功能（3.6 才做）。所以 3.5 只做設計稿裡「調整已知參數的
數值」這一小塊，其餘全部先不做——不是遺漏，是這個 App 現在的資料模型（`StrategyInfo.params`）撐不住
那些功能，硬做只會是假資料或連不到任何真實邏輯的假按鈕。

「套用參數」之後，狀態只停在 React state（`strategyConfig`），還沒有存檔、沒有送到 Rust、也還沒有任何
畫面在消費這個值——3.6 回測頁面實作時才會真的讀取它決定要跑哪個策略、哪組參數。這是團隊主管在派工時
明確要求的範圍：「先做表單狀態層面的串接就好」。

## 怎麼驗證

```bash
cd app
npm test        # Vitest：23 個測試全過（原本 8 個 + 新增 15 個）
npm run lint     # ESLint 零錯誤
npm run build    # tsc + vite build 成功
```

`StrategyParamForm.test.tsx` 涵蓋：

- 依 schema 動態產生對應數量與 label 的欄位（用 RSI 三個參數驗證，不是為 RSI 寫死斷言的表單結構）。
- integer 欄位擋下空白／非數字／零／負數／小數五種壞值，都不呼叫 `onApply`。
- 四條策略特定語意規則各自的壞值都被擋下：均線交叉快線≥慢線、布林通道倍數≤0、RSI 門檻超出 0～100、
  RSI 進場門檻≥出場門檻。
- 合法值變更後點「套用參數」，`onApply` 收到正確的 `Record<string, string>`。
- 「返回策略庫」呼叫 `onCancel`，不動 state。

`Strategies.test.tsx` 新增：點「調整參數」切到對應策略的表單（且只顯示那一個策略，不是四個都渲染）、
套用後回到列表並選中該卡片、返回不觸發 `onApplyConfig`。

離線／實跑驗證：用 Playwright 開 `npm run dev`，跟 3.4 一樣手動掛 `window.__TAURI_INTERNALS__.invoke`
的 mock 資料，實際點過一輪：

1. 列表畫面四張卡片都有「調整參數」按鈕（截圖確認）。
2. 點 RSI 的「調整參數」，表單顯示三個欄位、預設值正確。
3. 把「進場門檻」改成 120（超出 0～100），點「套用參數」，看到紅框 + 「RSI 門檻必須在 0 到 100 之間」
   錯誤訊息（截圖確認），`onApply` 沒有被呼叫（表單沒有跳走）。
4. 改成合法值 25，套用後回到列表，RSI 卡片變成金色邊框選中狀態（截圖確認）。
5. 再次點 RSI 的「調整參數」，表單顯示的是剛剛套用的 25、不是預設的 30——證明 `strategyConfig`
   狀態真的在 `App.tsx` 這一層持久，不是每次重新掛載都重置。

根目錄額外跑過 `cargo fmt --all -- --check`、`cargo clippy --all-targets -- -D warnings`、`cargo test`，
確認 195+10+3+1 個測試數量不變（這次改動一樣完全沒碰 `crates/` 或 `app/src-tauri`）。

## 建議閱讀順序

1. `app/src/strategyTypes.ts`：新增的 `StrategyConfig` 型別，看為什麼要有 `strategyId` + `values`
2. `app/src/StrategyParamForm.tsx`：先看 `integerError`/`decimalError`（通用型別驗證），
   再看 `fieldSemanticError`/`crossFieldError`（策略特定的語意規則，對照上面那張表）
3. `app/src/StrategyParamForm.test.tsx`：每個測試名稱就是一條驗證規則
4. `app/src/Strategies.tsx`：`editingStrategy` 怎麼決定要顯示列表還是表單、`initialValues`
   怎麼決定要用預設值還是已套用的值
5. `app/src/App.tsx`：`strategyConfig` 為什麼放在這一層

## 動手試試看

1. 在 `StrategyParamForm.tsx` 的 `fieldSemanticError` 裡，把 RSI 門檻上限從 100 改成 99，
   跑 `npm test` 看哪個測試失敗、失敗訊息長什麼樣，再改回來。
2. 把唐奇安突破的「進場週期」設成比「出場週期」小（例如 5 和 10），套用看看——會發現這是合法的，
   不會有錯誤訊息。對照 `donchian.rs` 的註解：唐奇安兩個週期本來就沒有大小限制，只是變成另一種
   （更敏感的）策略，不是錯誤。
