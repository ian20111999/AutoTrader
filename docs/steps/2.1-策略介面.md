# 2.1 策略介面 `Strategy`、`TargetPosition`

## 做了什麼

新增 `crates/core/src/strategy.rs`，只有兩個東西：

- **`TargetPosition`**：策略「想要」的部位，內部包一個 `Fixed`，是**帶正負號的比例**。
  - `TargetPosition::FLAT`（`0`，空手）、`TargetPosition::FULL_LONG`（`1`，滿倉做多）。
  - `long(0.5)` 半倉做多、`short(0.5)` 半倉做空（`-0.5`）、`new(2)` 兩倍槓桿做多。
  - `ratio()` 取回帶正負號的比例、`is_flat()` 問是不是空手。
- **`Strategy` trait**：
  - `on_bar(&mut self, bar: &Bar) -> TargetPosition`：每根 K 線收盤呼叫一次，回傳這根收盤後想持有的目標部位。
  - `warmup_bars(&self) -> usize`（預設 `0`）：至少要先餵幾根 K 線，訊號才有意義。

這一步**沒有**任何具體策略、沒有回測迴圈、沒有下單、沒有手續費——那是 2.2、2.3、2.4、2.7 的事。

## 為什麼這樣設計

### 回傳「目標部位」而不是「訂單」

策略只回答「我想要多少倉位」，不回答「送什麼單」。
要怎麼從現在的部位變成目標部位（要買多少、數量怎麼取整到交易所的級距、
成交價算哪一根的開盤），是 2.3 成交模擬與 1.3 `SymbolRules` 的工作。

好處是同一份策略程式可以原封不動跑在回測、模擬交易、測試網、實盤四種模式，
換交易所規則也不用改策略。

### 歷史由策略自己記，呼叫端不用知道誰要看幾根

均線交叉要 N 根、RSI 要 14 根、布林通道要 20 根、唐奇安突破要 55 根——
每個策略需要回顧的長度都不一樣。兩種做法：

| 做法 | 缺點 |
|---|---|
| 呼叫端餵一整段歷史（`on_bar(&[Bar])`） | 回測迴圈得先問每個策略「你要幾根」，還要幫忙切片；實盤時等於要一直重算整段歷史 |
| **策略自己維護 rolling window（採用）** | 策略實作要自己記狀態（所以 `on_bar` 是 `&mut self`） |

採用第二種：呼叫端只做「一根一根餵進去」，這樣回測迴圈與實盤的餵法完全一樣，
策略也可以用累加值（例如移動總和）做到 O(1) 更新，不必每根重算。

`warmup_bars()` 是搭配用的**宣告**，不是保護機制：

- 回測迴圈（2.2/2.6）可以用它把暖機期排除在績效統計外，不然前 N 根強制空手會稀釋年化報酬。
- 之後的桌面介面可以用它提醒「這個參數需要至少 55 根 K 線，你選的區間不夠」。
- 但資料不夠時，**策略自己仍然必須安全回傳空手**，不能 panic。
  測試 `strategy_needing_history_stays_flat_until_warmed_up` 就是在釘這條規則。

### 部位型別為什麼不是布林開關

現貨目前只需要「做多或空手」，寫成 `bool` 最省事——但 2.5 之後合約要做空、要槓桿，
那時介面就得整個改，連帶所有策略都要改。所以現在就用帶正負號的 `Fixed`：

- 正數做多、負數做空、`0` 空手，`1` 是滿倉、`2` 是兩倍槓桿。
- 用「比例」而不是「幾顆 BTC」：策略不該知道帳戶有多少錢，也不該知道交易所的數量級距。
- `Default` 是 `FLAT`：忘記設定的後果是空手，不是不小心開了一個倉。
- `long()` / `short()` 會把大小取絕對值，所以「符號寫錯變成做反方向」這種錯不會發生。

### `on_bar` 不回傳 `Result`

策略拿到的是已經驗證過的 `Bar`，算不出訊號（暖機不足、數值異常）時正確的反應是
**回傳空手**，不是讓整個回測中斷。把這件事寫進 trait 的契約裡，比讓每個呼叫端
去處理一個永遠不該發生的錯誤更清楚。

### `Strategy` 是 object-safe

沒有泛型方法、沒有回傳 `Self`，所以可以 `Box<dyn Strategy>`。
2.2 的回測迴圈與之後介面的「策略庫」都要拿一串不同策略跑同一份資料，
測試 `strategies_can_be_stored_as_trait_objects` 把這個性質釘住，
以免之後有人加了泛型方法，不小心讓它不能裝箱。

## 怎麼驗證

```bash
cargo test -p at-core strategy
```

應該看到 9 個 `strategy::tests::...` 全部 `ok`。全部測試 `cargo test` 共 69 個。

測試裡有四個「假策略」，用來證明介面本身呼叫得動：

| 假策略 | 驗證什麼 |
|---|---|
| `AlwaysLong` / `AlwaysFlat` | 最簡單的實作只要寫一個 `on_bar`，`warmup_bars()` 預設是 0 |
| `Alternating` | 策略可以保存自己的狀態（每 N 根切換多空），回傳值符合預期順序 |
| `HigherThanWindowStart` | 需要回顧歷史的策略：自己維護 rolling window，暖機期回空手 |

## 建議閱讀順序

1. `strategy.rs` 最上面的三點設計說明
2. `TargetPosition`：為什麼是帶正負號的比例
3. `Strategy` trait 的兩個方法與註解裡「呼叫端保證 / 實作端保證」
4. 測試裡的 `run()` 輔助函式——那三行就是 2.2 回測迴圈餵資料的方式
5. 測試 `HigherThanWindowStart`：真實策略（2.7）大概長這樣

## 動手試試看

1. 自己加一個假策略 `AlwaysHalfShort`（永遠 `TargetPosition::short(fx("0.5"))`），
   用 `run()` 餵三根 K 線，先猜回傳值再跑測試。
2. 把 `HigherThanWindowStart::on_bar` 裡的「資料不足回傳空手」那三行刪掉，
   跑 `cargo test`。它**不會** panic，而是第 2 根就拿只有 2 根的視窗算出「做多」
   （`101 > 100`）——測試會在這裡抓到它。這才是暖機期真正的危險：
   不是程式壞掉，是安靜地多做了幾筆本來不該做的交易，回測數字看起來還很正常。
3. 在 `Strategy` trait 裡加一個回傳 `Self` 的方法，跑 `cargo test`，
   看 `strategies_can_be_stored_as_trait_objects` 怎麼編譯失敗，再改回來。
