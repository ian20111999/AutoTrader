# 6.4 把策略執行接上測試網下單

新 crate `at-testnet-trading`：把 4.5 的即時行情、2.1 的策略介面、6.3 的風控閘門、6.2 的
測試網下單 client 串成一個「送出去 → 等回報 → 更新帳本」的自動交易迴圈。

這一步**不做畫面**（那是 6.5），也**沒有真的連過測試網**（那是 6.6，需要使用者的測試網金鑰）。

## 做了什麼

兩個檔案：

| 檔案 | 角色 |
|---|---|
| `crates/testnet-trading/src/trader.rs` | 核心邏輯：部位差值換算、風控串接、送單、等回報、更新帳本。沒有執行緒、沒有 channel、沒有系統時鐘 |
| `crates/testnet-trading/src/lib.rs` | 接線：`spawn()`／`TestnetTradingHandle`／背景迴圈，和 5.3 的 `at-paper-trading` 同一個形狀 |

一根收盤 K 線的處理順序（`Trader::on_closed_bar`）：

1. 用收盤價評價權益（`現金 + 部位 × 收盤價`），回報給 `DailyPnl` 取得今日損益。
2. **問策略**（`strategy.on_bar(bar)`）拿目標部位——**不管閘門會不會擋都要問**。
3. 算出這根要送什麼單：
   ```text
   目標數量 = 目標比例 × 權益 ÷ (收盤價 × (1 + 吃單費率))   // 往下取整到數量級距
   要成交的量 = 目標數量 − 目前數量                          // 正數買、負數賣
   ```
   取整用 `SymbolRules::qty_for_quote`／`round_qty`（不自己重寫取整），取整後是 0 就不下單。
4. `SymbolRules::check()` 驗合規（數量級距、上下限、最小金額）。不合規就回報
   `OrderOutcome::Invalid(原因)` 跳過這一根，不硬送給交易所拒絕。
5. `RiskLimits::check()` 過閘門。擋下就記一筆 `OrderOutcome::Blocked(原因)`、**不重試**。
6. 通過才呼叫 `BinanceTestnetClient::place_market_order()`。回應不是終態
   （`FILLED`/`CANCELED`/`REJECTED`/`EXPIRED`/`EXPIRED_IN_MATCH`）時，用
   `query_order` 做有限次數、有退避、每 50 ms 檢查停止旗標的輪詢（退避 100/200/400/800/1600 ms，
   最多 5 次、總共 3.1 秒）。
7. 用交易所回報的 `executedQty`／`cummulativeQuoteQty` 更新現金、部位、成交筆數。

往外送的事件：`TestnetUpdate::{Order, Bar, Stopped, Failed}`。同一根 K 線如果有下單這件事，
`Order` 排在 `Bar` 之前，所以畫面可以先記 log 再更新數字。

### 結構上就不可能繞過閘門

整個 crate 只有 `Trader::send_gated_order`（私有）會呼叫 `place_market_order`，而它的
第一件事就是 `RiskLimits::check`。`place_market_order` 以外的呼叫端一個都沒有：

```rust
fn send_gated_order(&mut self, side: Side, qty: Fixed, price: Fixed, daily_pnl: Option<Fixed>)
    -> Result<OrderOutcome, TradingError>
{
    // ...組 AccountState / ProposedOrder...
    if let Err(blocked) = self.limits.check(&state, &order) {
        self.blocked += 1;
        return Ok(OrderOutcome::Blocked(blocked));
    }
    let placed = self.gateway.place_market_order(...)?;
```

要繞過閘門必須改這個私有函式的前幾行，沒有「某個呼叫端忘記檢查」這種可能。
送單對象也只有 6.2 的 `BinanceTestnetClient`（網址寫死在常數）；這個 crate 從頭到尾
沒有提到正式環境的 `BinanceClient`。

## 為什麼這樣設計

### 為什麼不是把 `PaperEngine` 包一層

5.1 的 `PaperEngine` 是「同步、確定性」的：給它目標部位，它當場算出成交價、當場改完帳本。
真實下單沒有這種好事——送出去之後成交價、成交量、成交金額都是交易所說了才算，還可能部分
成交或被拒絕。把「假設立刻成交」的引擎套在真實下單上，帳本會變成兩套數字（引擎以為的 vs
交易所實際的），之後每一次調倉都建立在錯的部位上。所以這裡另寫一套流程，只跟 5.x 共用
**策略介面**、**型別**和「只有收盤 K 線才處理」這個規則。

### 本地帳本怎麼從無到有（決定一）

**起始現金由使用者在啟動時提供**（`TestnetConfig::initial_cash`），比照 5.4 模擬交易頁面
要求輸入虛擬資金的做法。

理由是沒得選：4.x 只做了唯讀的費率／下單規則／行情同步，**沒有查帳戶餘額的端點**，所以
`AccountState.daily_pnl` 與權益不可能從交易所即時查到。既然必須在本地記一本帳，起點就只能
由使用者給一個參考值；之後每一筆**真實成交回報**更新它（這是和 `PaperEngine` 唯一的差別，
也是最重要的差別）。

`DailyPnl` 在**第一根收盤 K 線**才建立，日界用的是**行情事件自帶的交易所時間**
（`KlineUpdate::event_time_ms`），不讀本機時鐘——UTC 日界要和 Binance 對得上，而且測試可以
餵任意假時間。

**已知限制（需要使用者知道）**：重開程式會重置今日損益。帳本沒有持久化，所以「今天已經虧到
上限」這件事活不過一次重啟。要補這個洞需要把帳本存進 1.6 的本機儲存，那是 6.5／6.6 再決定
的事，不在這一步。

### 手續費自己估，不信任測試網回報（決定二）

測試網是沙盒，回報的手續費常常是 0；6.2 也刻意沒有解析 `fills` 明細陣列。這裡改用
`at-core::FeeSchedule`（搭配 4.3 從**正式環境帳戶**同步到的真實費率）估算：

```text
手續費 = 交易所回報的成交金額（cummulativeQuoteQty） × 吃單費率
```

兩個理由：

1. **使用情境是「之後接正式環境會長怎樣」。** 用測試網的 0 手續費跑出來的權益曲線，會讓人
   以為這個策略的交易成本不存在——那正是 2.4 花一整步處理的事。寧可在測試網就看到真實成本。
2. **四種模式的成本算法要一致。** 回測、模擬、測試網都走 `FeeSchedule`，數字才對得起來；
   測試網一套、回測另一套的話，「測試網的結果能不能推論到正式環境」就沒有答案。

代價寫清楚：這個手續費是**估算值**，不是交易所實際扣的錢。真的要對帳（例如正式環境），要
解析 `fills[].commission` 與 `commissionAsset`（含 BNB 抵扣要折成 USDT），那是第 7 步的事。

算目標數量時費率一律用**買方吃單費率**，不分這一筆是買是賣：目的是留住付手續費的錢，寧可
少買一點，也不要算出一個「現金付不出手續費」的數量。

### 一鍵停止與停止是兩個獨立的開關（決定三）

- `TestnetTradingHandle::set_kill_switch(bool)`：**只擋送單**。行情連線繼續跑、快照繼續
  更新、策略繼續看每一根 K 線。
- `TestnetTradingHandle::stop()`：真正收工。和 5.3 一樣設的是
  `MarketStreamHandle::stop_flag()` 交出來的同一個旗標，所以按一次會連 WebSocket 一起結束。

分成兩個開關是因為 6.3 文件裡「一鍵停止是因為不再相信這套自動化」的精神：使用者要的是
「別再幫我下單」，不是「把螢幕關掉」。還看得到即時部位與權益，才有辦法決定接下來手動處理
什麼。反過來說，一鍵停止期間策略仍然每根都被問到——指標的 rolling window 少一根就全錯了，
「今天不下單」不等於「今天不看盤」。

一鍵停止**不會**撤掉已經送出去的單（它已經在交易所了），擋的是下一張；正在等回報時按停止會
收到 `TradingError::StoppedWhileWaiting`，提醒你去確認那張單的下場。

### 不確定就停止整個迴圈（fail closed）

下面三種情況回 `TestnetUpdate::Failed` 並結束串流，不是「跳過這一根繼續跑」：

| 情況 | 為什麼是致命的 |
|---|---|
| `PlaceFailed`：送單請求本身失敗 | 訂單**可能已經進交易所**（回應在路上掉了也算）。本地帳本和實際部位可能已經不一致，繼續用一本可能是錯的帳交易，比停下來危險得多 |
| `OrderNotFinal`：輪詢用完還沒到終態 | 這張單可能還會繼續成交，帳本已經追不上 |
| `StoppedWhileWaiting`：等回報時使用者喊停 | 同上，這張單的下場不明 |

三種情況都會**先把已經回報的成交量記進帳本**才往外通報——漏記已成交的量，之後每一筆調倉都
會算錯。查單失敗不算致命：查單是唯讀、可重複的操作，失敗就用掉一次退避額度再試。

### 其他取捨

- **現貨不能做空**：策略回負的目標部位時當成空手處理（只賣到 0，不會賣出超過持倉的量）。
  合約做空是之後的範圍。
- **訊號在收盤產生、立刻送市價單**。這跟回測「下一根開盤成交」的假設不同，是刻意的：回測
  那樣寫是為了避免偷看未來（看到收盤價才決定、卻用那個價格成交），真實世界在收盤的瞬間就
  能把單送出去，沒有理由自己延後一根。
- **只做現貨市價單、單一交易對、單一 session**，同 5.x 的範圍取捨。

## 怎麼驗證

```bash
cargo fmt --all
cargo clippy --all-targets -- -D warnings
cargo test -p at-testnet-trading
```

27 個測試全過（另有 1 個需要金鑰與網路的 `#[ignore]` 測試）。涵蓋：

- 正常買進／回到空手／目標沒變就不重送單／低於最小金額就跳過；
- 一鍵停止期間一張單都不送、但策略照樣看到每一根 K 線；
- 虧損達上限時擋下加碼、放行平倉；
- `NEW` → `PARTIALLY_FILLED` → `FILLED` 的輪詢、輪詢逾時、等回報時喊停、查單失敗後重試；
- 被拒絕的單不動帳本、部分成交只記真的成交的量、送單失敗不動帳本；
- 收盤價不是正數是錯誤而不是除以零、今日損益跨 UTC 日歸零；
- `stop()` 會連帶讓行情連線收工、`set_kill_switch()` 不會。

這些測試都用假交易所（`OrderGateway` 的測試實作）＋普通的 `mpsc::channel` 當行情來源，
完全不連網路。

想確認測試真的有在測東西，可以做兩個突變實驗（都驗證過會讓測試變紅）：

1. 把 `send_gated_order` 裡的 `self.limits.check(...)` 拔掉 → 3 個測試失敗（含兩個
   一鍵停止的測試）。
2. 把 `apply_fill` 裡的 `response.executed_qty` 換成 `requested_qty`（也就是「假設送出去的
   量就是成交的量」）→ 3 個測試失敗。

## 跨模型審查後補強的兩個 fail-closed 檢查

Claude QA 跟 Codex 各自獨立審查過一輪，結論都是「沒有阻斷性問題」，但 Codex 指出
`apply_fill` 有兩個跟這個模組自己宣稱的「判不出來就擋」原則不一致的小漏洞，已經補上：

1. **賣出量不可能超過帳上持倉**——真實 Binance 現貨不會讓賣單成交超過實際餘額（餘額不足
   直接拒絕），但帳本邏輯不該假設下游永遠遵守這件事。原本 `checked_sub` 算得出負的部位就
   照樣接受，之後 `plan_order` 會拿一個已經錯的部位繼續算、錯誤越滾越大。現在賣出前先比較
   `executed > self.position`，超過就回 `TradingError::Arithmetic`、帳本完全不動。
2. **成交量跟成交金額必須同時是 0 或同時不是 0**——交易所回應理論上不會「有成交量卻沒有
   成交金額」或反過來，但這是外部輸入，不該假設它永遠自洽。原本只檢查兩者是否為負數，
   現在加一個 `executed.is_zero() != quote.is_zero()` 的檢查，不自洽就當成算不出來，擋下
   整個迴圈。

兩個都補了對應測試（`a_response_with_executed_qty_but_no_quote_is_rejected_as_inconsistent`、
`a_sell_cannot_apply_a_fill_larger_than_the_tracked_position`），加上去之後是 29 個測試
全過（原本 27 個 + 這 2 個）。

## 建議閱讀順序

1. `crates/testnet-trading/src/lib.rs` 開頭的模組說明：為什麼不包 `PaperEngine`、兩個開關的
   分工、本地帳本是怎麼回事。
2. `trader.rs` 的 `Trader::on_closed_bar`：一根 K 線的七個步驟就是程式碼本身的順序。
3. `trader.rs` 的 `Trader::send_gated_order` 與 `await_final`：唯一的送單路徑，以及等回報的
   退避／停止旗標處理。
4. `trader.rs` 的 `Trader::apply_fill`：帳本怎麼吃交易所的回報。
5. 和 `crates/paper-trading/src/lib.rs` 對照看 `spawn`／`run`，會發現接線的形狀幾乎一樣，
   差別全在中間那顆引擎。

## 動手試試看

1. 把 `plan_order` 裡「負的目標部位當成空手」那段拿掉，重跑測試，看
   `a_short_target_is_treated_as_flat_on_spot` 怎麼失敗——理解現貨為什麼不能照抄合約的算法。
2. 把 `POLL_BACKOFF_MS` 改成空陣列，重跑 `a_non_final_status_is_polled_until_it_becomes_final`，
   看「完全不輪詢」會把一張 `NEW` 的單變成什麼結果。
3. 想一個「帳本會和交易所不一致」的情境（例如送單回應掉了、程式中途被砍掉），想想要補什麼
   才能自動對帳——這會是之後接正式環境必須先解決的問題。
