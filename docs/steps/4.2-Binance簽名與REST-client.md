# 4.2 Binance REST client 骨架＋簽名機制

新增 `crates/binance-client`（package 名稱 `at-binance`），提供 HMAC-SHA256 簽名與一個能打
Binance SIGNED 端點的 client 骨架。這一步只碰唯讀端點，沒有任何送出訂單/修改帳戶設定的程式碼
路徑。

## 做了什麼

新增一個 crate：

- `crates/binance-client/Cargo.toml`：依賴 `at-secrets`（讀 Keychain）、`hmac` 0.13、`sha2`
  0.11（RustCrypto 官方的 HMAC/SHA-2 實作，`cargo search` 確認的目前版本）、`ureq` 3（跟
  `at-downloader` 一致，沒有另外引入別的 HTTP client）。
- `crates/binance-client/src/lib.rs`：
  - `sign(secret, query) -> String`：對 query string 做 HMAC-SHA256，回傳小寫 hex 字串。
  - `build_signed_query(secret, params, timestamp_ms)`：組出「業務參數 + `recvWindow` +
    `timestamp`」的查詢字串，簽名後附上 `signature=...`。
  - `BinanceClient`：`new`（直接給金鑰）、`from_keychain`（讀 4.1/4.6 存的
    `com.autotrader.app.binance-readonly-api-key`/`-api-secret`，帳號 `autotrader`）、
    `signed_get(path, params)`（打一個簽名過的 GET，回傳原始 JSON 字串）。
  - `BinanceError`：憑證讀取失敗、金鑰未設定、系統時間異常、HTTP 失敗、讀回應失敗五種，訊息
    全部是固定中文說明。
- 根目錄 `Cargo.toml`：`members` 加上 `crates/binance-client`。

## 為什麼這樣設計

### 簽名規則的查證來源

Binance 官方文件（[General API Information](https://developers.binance.com/docs/binance-spot-api-docs/rest-api/general-api-information)）：
簽名負載是「查詢字串（+ HTTP body，這裡用不到）」，用 API Secret 當 HMAC-SHA256 的 key，
輸出編碼成 hex；header 是 `X-MBX-APIKEY`；`timestamp` 必填（毫秒），`recvWindow` 選填、預設
5000、最大 60000。

文件裡附的官方範例（secret、query string、預期簽名）被當成離線單元測試的已知答案：

```
secret: NhqPtmdSJYdKjVHjA7PZj4Mge3R5YNiP1e3UZjInClVN65XAbvqqM6A7H5fATj0j
query : symbol=LTCBTC&side=BUY&type=LIMIT&timeInForce=GTC&quantity=1&price=0.1&recvWindow=5000&timestamp=1499827319559
簽名  : c8db56825ae71d6d79447849e617115f4a920fa2acdcab2b053c4b2838bd6b71
```

寫程式碼之前先用 Python 的 `hmac`/`hashlib` 離線覆算過一次確認這組範例本身正確，才拿來當
測試固定答案——避免抓錯文件版本或抄錯字元卻永遠不會被抓到。

### `hmac`/`sha2` 版本與 API

`cargo search` 確認目前版本是 `hmac = "0.13.0"`、`sha2 = "0.11.0"`（RustCrypto 官方 crate，
`at-secrets` 的 `keyring` 之外這專案第一次引入密碼學 crate，選這兩個是因為它們是 Rust 生態
系裡 HMAC-SHA256 事實上的標準實作、被最多其他密碼學 crate 依賴）。API 用法用 context7 查
`docs.rs/hmac` 確認：`Hmac<Sha256>::new_from_slice` 建 mac，`update`/`finalize` 算結果，
`into_bytes()` 拿原始 bytes。0.13 版的 `new_from_slice` 是 `KeyInit` trait 提供的，光
`use hmac::{Hmac, Mac}` 不夠，要多 `use hmac::KeyInit`（第一次 `cargo build` 直接編譯錯誤
確認了這件事，不是憑印象猜的）。

hex 編碼沒有另外引入 `hex` crate：Binance 只要 32 bytes 轉小寫 hex 這種簡單需求，
`bytes.iter().map(|b| format!("{b:02x}")).collect()` 一行打完，不需要為了這個多一個依賴
（ladder：「能一行解就不裝套件」）。

### 為什麼只做「打簽名過的 GET，回傳原始 JSON 字串」

這一步的任務是「REST client 骨架＋簽名機制」，不是「串某個特定端點的完整資料模型」——4.3
（帳戶費率）跟 4.4（下單規則）各自要把 JSON 反序列化成 `FeeSchedule`/`SymbolRules` 對應的
結構，如果這裡先定義一套自己的 response struct，4.3/4.4 大機率要重新設計欄位或整個丟掉。先
回傳 `String`，讓後面的步驟自己決定要用 `serde_json::Value` 還是專屬 struct 反序列化，不在
還沒看到真正需求之前先猜。

### ponytail：沒有做通用的 URL 百分比編碼

`build_signed_query` 直接把參數值原樣接進查詢字串，沒有處理非 ASCII 字元的百分比編碼。
Binance 這幾個唯讀端點（`account`、`account/commission`、之後的 `exchangeInfo`）用到的參數
值都是幣種代碼、數字、`BUY`/`SELL`/`LIMIT` 這類英數字組合，不會有中文或特殊符號。真的需要
傳非 ASCII 值時再補 `percent-encoding` 這類處理，現在先不做這個目前用不到的一般化。

### 安全設計：錯誤訊息、`Debug` 都不含敏感內容

- `BinanceError` 的每個變體都是固定中文說明或 HTTP 狀態碼，沒有任何一個變體把 URL、query
  string、簽名或 `api_secret` 塞進去。
- 查過 `ureq` 3.x 的 `Error` enum 每個變體的 Display 格式（例如 `StatusCode(u16)` 只印
  `http status: {code}`，`Timeout`/`Io`/`HostNotFound` 等等都不含請求 URL）——確認直接
  `.to_string()` 轉傳輸層錯誤不會意外洩漏簽名過的 URL，才放心在 `signed_get` 的錯誤分支這樣
  寫。
- `signed_get` 组好 `url`（含簽名）之後只用來呼叫 `ureq::get(&url)`，沒有任何路徑會把這個
  變數印出來或塞進錯誤訊息。
- 測試 `error_display_never_contains_the_secret` 延續 4.1/4.6 同樣的檢查精神。

## 真實金鑰驗證：已經打通

實作當下這個背景 agent 的沙盒權限分類器擋下了「打 Binance 正式環境」的 Bash 指令（歸類成
「Production Reads」，指令執行前就被拒絕），沒有嘗試繞過——把簽名過的 URL 丟給其他工具（例如
通用的網頁抓取工具）等於把 API Secret 算出來的簽名結果送去一個不受信任的第三方中介服務，這比
「這次沒驗證成功」的風險高得多，不值得這樣做。

協調端（權限層級不同，沒有被同一個分類器擋下）之後手動跑了：

```bash
cargo test -p at-binance -- --ignored --nocapture
```

`signed_get_account_commission_against_real_binance` **通過**，10.36 秒內對正式環境的
`GET /api/v3/account/commission` 打了一次真實簽名請求，拿到含 `standardCommission` 欄位的
回應——證實整條「讀 Keychain → 組簽名 → 打 HTTP → 收到回應」的鏈路真的通。這次沒有遇到 4.1
記錄過的 Keychain 互動授權對話框問題（那個限制仍然存在，只是這次執行環境剛好已經授權過，或
沒有觸發——如果你在全新環境第一次跑，還是可能遇到，屬於另一件事）。

## 給 4.3（帳戶實際費率同步）的銜接說明

4.3 要做的事：定期（每 24h）打 `GET /api/v3/account/commission`（需要 `symbol` 參數，例如
`BTCUSDT`），把回應反序列化成對應 1.4 `FeeSchedule` 的欄位（`standardCommission.maker`/
`taker` 等），成功就更新，失敗就沿用上次的值並記下這次失敗的日期。串接方式：

```rust
let client = at_binance::BinanceClient::from_keychain()?;
let body = client.signed_get("/api/v3/account/commission", &[("symbol", "BTCUSDT")])?;
// body 是原始 JSON 字串，4.3 自己定義一個對應的 struct 用 serde 反序列化，
// 或先用 serde_json::Value 拿需要的欄位——這個 crate 不預設任何回應結構。
```

`BinanceClient::from_keychain()` 讀不到金鑰時會回傳 `BinanceError::MissingCredential`，4.3
的錯誤訊息應該引導使用者回到 4.6 的「連線設定」分頁，而不是顯示抽象的「認證失敗」。

## 建議閱讀順序

1. `crates/binance-client/src/lib.rs` 的 `sign`/`build_signed_query`：純函式、跟網路和
   Keychain 都無關，先確認簽名邏輯本身。
2. `BinanceClient::from_keychain`/`signed_get`：怎麼把簽名接到實際的 HTTP 請求。
3. 測試模組最下面的 `signed_get_account_commission_against_real_binance`（`#[ignore]`，已
   確認對真實帳戶打通過）：之後要重新確認連線還通不通時執行這個。

## 動手試試看

1. 把 `crates/binance-client/src/lib.rs` 裡官方範例的 query string 改一個字元（例如
   `quantity=1` 改成 `quantity=2`），重跑 `cargo test -p at-binance`，看
   `sign_matches_binance_official_example` 會不會失敗——確認測試真的在檢查簽名內容，不是
   剛好兩邊都算錯但湊巧一樣。
2. 跑一次 `cargo test -p at-binance -- --ignored --nocapture`，看能不能打到 Binance 拿到
   手續費資料（第一次在全新環境讀取既有 Keychain 憑證，可能遇到 4.1 記錄過的互動授權對話框，
   需要有畫面的環境點一次「永遠允許」）。
