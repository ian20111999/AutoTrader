# 1.7 下載器 `download_monthly_klines`、`download_and_store_monthly_klines`

## 做了什麼

新增一個新的 crate `crates/downloader`（package 名稱 `at-downloader`），裡面一個檔案 `src/lib.rs`：

- **`monthly_kline_url(symbol, interval, year, month)`**：組出 Binance 現貨月線 zip 的下載網址，例如 `https://data.binance.vision/data/spot/monthly/klines/BTCUSDT/1m/BTCUSDT-1m-2024-01.zip`。
- **`download_monthly_klines(symbol, interval, year, month)`**：組網址 → HTTP 下載 zip → 解壓 → 用 1.5 的 `parse_klines_csv` 解析，回傳 `Vec<Bar>`（不存檔）。
- **`local_path(base_dir, symbol, interval, year, month)`**：算出這個月的資料該存在本機的哪個路徑。
- **`download_and_store_monthly_klines(symbol, interval, year, month, base_dir)`**：下載 + 用 1.6 的 `write_bars_file` 存檔，回傳 `(Vec<Bar>, PathBuf)`。
- **`DownloadError`**：下載、解壓、解析、存檔任一步驟失敗的原因（`InvalidMonth`、`Http`、`Zip`、`UnexpectedEntryCount`、`Csv`、`Store`、`Io`）。

目前只支援**現貨市場的月線**（`data/spot/monthly/klines/...`）。data.binance.vision 也有 daily 版本與合約市場的路徑，格式類似（只是網址前綴不同），但這一步沒有用到，先不加——等回測引擎真的需要逐日下載或需要合約資料時再補，不先幫還沒用到的東西打地基。

## 為什麼放新的 crate，不放進 `crates/core`

`at-core` 目前定位是「共用型別」，到 1.6 為止零第三方依賴（見 1.6 文件的設計決定）。下載器需要 HTTP client 與 zip 解壓，這兩件事標準函式庫都沒有，勢必要加外部套件——但這是「主動發網路連線」的功能性模組，跟「型別定義」是不同層次的東西：如果把 `ureq`、`zip` 這兩個依賴放進 `at-core`，之後任何只需要 `Fixed`、`Bar` 這些型別的地方（例如之後的桌面 App 前端邏輯、或用不到下載功能的測試）都會被迫多編譯、多打包這兩個依賴。獨立成 `at-downloader`（依賴 `at-core`）讓「型別」與「網路下載」的依賴範圍分開，需要下載功能的人（`engine`、之後的桌面 App）才去依賴它。

沒有放進 `crates/engine`：`engine` 目前是執行檔骨架（`main.rs`），下載邏輯本身沒有理由跟執行檔綁在一起，寫成獨立的 library crate 才能被之後的回測引擎、桌面 App 各自呼叫、也才能各自單獨測試。

## 選用的外部依賴

- **[`ureq`](https://crates.io/crates/ureq)（v3）—— HTTP client**：同步、沒有非同步 runtime 依賴（這個 workspace 目前也沒有 async runtime，不需要為了一次 HTTP GET 拉進 tokio）。預設功能就包含 TLS（`rustls`）與 gzip，`https://data.binance.vision` 直接能打。考慮過 `reqwest`：功能更完整但預設是非同步、依賴樹大很多（tokio 全家桶），對「下載一個 zip 檔」這種單次同步請求是過度的。也考慮過自己拉 `std::net::TcpStream` + 手刻 HTTP/TLS：TLS handshake 不是能合理手刻的東西，放棄。
- **[`zip`](https://crates.io/crates/zip)（v4，`default-features = false, features = ["deflate"]`）—— zip 解壓**：只需要「讀」單一檔案的能力，不需要寫入/加密/多種壓縮演算法，所以關掉預設的 `aes-crypto`、`bzip2`、`lzma`、`zstd`、`xz` 等功能，只留 Binance zip 實際會用到的 `deflate`，減少依賴樹與編譯時間。沒有考慮手刻 zip 解析：zip 格式（local file header、中央目錄、CRC）比 CSV 複雜很多，手刻換來的收益遠不及風險。

## 流程

```
monthly_kline_url()          組網址（純字串邏輯，不連網路）
        │
        ▼
fetch_bytes()                HTTP GET，回傳整個回應 body 的 bytes（就是 zip 檔內容）
        │
        ▼
extract_single_csv()         用 zip::ZipArchive 開檔、確認裡面剛好 1 個檔案、讀成字串
        │
        ▼
parse_klines_csv()           1.5 已經寫好的 CSV 解析器，回傳 Vec<Bar>
        │
        ▼
write_bars_file()            1.6 已經寫好的本機存檔（只在 download_and_store_monthly_klines 才做這步）
```

`download_monthly_klines` 只做到 `parse_klines_csv` 那一步（回傳 `Vec<Bar>`，不存檔），`download_and_store_monthly_klines` 才多做存檔。這樣呼叫端如果只是想看一下資料、不想真的存到硬碟（例如寫一次性的檢查腳本），可以只呼叫前者。

## 幾個設計決定

- **HTTP 下載獨立成 `fetch_bytes` 一個小函式**：把「打網路」跟「組網址」「解壓」「解析」分開，是因為只有 `fetch_bytes` 真的需要網路，其他三段都是純邏輯，可以在不連網路的情況下單獨測試（見下面「怎麼驗證」）。沒有做成可替換的 trait/寫成泛型注入 HTTP client：目前只有一個呼叫端、一種用法，`fetch_bytes` 內部只有三行、沒有分支邏輯，加一層抽象換不到測試上的好處（真正會壞的地方是「網路那次真實請求」，不是這三行的邏輯本身），等真的有第二種 HTTP 需求或需要在測試裡模擬各種 HTTP 錯誤情境時再考慮。
- **zip 裡應該剛好 1 個檔案，數量不對就回錯誤，不是隨便挑一個**：這是外部資料（來自網路），照過去 1.5、1.6 的原則——資料一有不對勁就整體回傳錯誤，不要悄悄用「可能不是預期的那個檔案」的資料繼續跑。
- **月份用 `1..=12` 驗證，不合法直接回 `InvalidMonth`**：避免組出一個保證 404 的網址才在下載階段才發現參數打錯。
- **不重新驗證 `Bar`**：`parse_klines_csv` 內部已經呼叫 `Bar::validate`（1.5 做過的事），下載器不重複做。
- **儲存路徑用 `<base_dir>/<SYMBOL>/<interval>/<SYMBOL>-<interval>-<year>-<month>.csv`**：按幣種、週期分資料夾，同一個幣種、週期的每個月各自一個檔案，之後要找某一段歷史資料時，路徑本身就能告訴你在哪裡（不需要另外維護一份索引）。副檔名維持 `.csv`（逗號分隔），雖然欄位數跟 Binance 原始 CSV 不同（6 欄，1.6 的格式），但延續 1.6 的作法沒有另外發明副檔名。

## 怎麼驗證

不連網路的部分（URL 組裝、zip 解壓、CSV 解析、路徑計算）：

```bash
cargo fmt --all
cargo clippy --all-targets -- -D warnings
cargo test -p at-downloader
```

`at-downloader` 應該看到 10 個測試全過、1 個標成 `ignored`（真正連網路的整合測試）。全部測試 `cargo test` 目前共 104 個（94 個 `at-core` + 10 個 `at-downloader`）。

實際連網路的整合測試（`downloads_a_real_month_from_binance`，下載 BTCUSDT 2024-01 的日線）標了 `#[ignore]`，不在預設的 `cargo test` 跑，手動執行：

```bash
cargo test -p at-downloader -- --ignored
```

實際跑過的結果：

```
running 1 test
test tests::downloads_a_real_month_from_binance ... ok
```

驗證了 31 根 K 線（2024-01 有 31 天）、第一根開盤時間是 `1704067200000`（2024-01-01 00:00 UTC）。這個測試選用 D1（日線）而不是 1m：一個月只有約 30 行，下載的 zip 檔只有幾 KB，跑得快、不浪費頻寬。

## 建議閱讀順序

1. `lib.rs` 最上面的說明：整體流程、為什麼目前只做現貨月線
2. `monthly_kline_url`：URL 怎麼組出來，月份怎麼驗證
3. `extract_single_csv`：zip 裡只有 1 個檔案這個假設，以及不成立時怎麼回錯誤
4. `download_monthly_klines` / `download_and_store_monthly_klines`：兩者只差最後一步存檔
5. 測試 `download_monthly_klines_parses_the_zip_end_to_end`：不連網路，直接用記憶體中的 zip 驗證「解壓 → 解析」接得起來
6. 測試 `downloads_a_real_month_from_binance`（標 `#[ignore]`）：真正打網路的樣子

## 動手試試看

1. 手動執行 `cargo test -p at-downloader -- --ignored`，看真的下載成功的樣子；改成別的幣種（例如 `ETHUSDT`）或別的週期，看結果會不會變。
2. 呼叫 `download_and_store_monthly_klines`，存到 `data/` 資料夾下，用檔案總管或 `cat` 打開存出來的檔案，跟 1.6 `format_bars` 的格式比對一下（6 欄、逗號分隔）。
3. 故意傳一個不存在的幣種（例如 `Symbol::new("NOTAREALCOIN").unwrap()`），呼叫 `download_monthly_klines`，看 Binance 回什麼狀態碼、`DownloadError::Http` 訊息長什麼樣。

## 下一步銜接

`download_and_store_monthly_klines` 存出來的檔案，格式跟 1.6 的 `write_bars_file` 完全一樣，所以之後 2.x 回測引擎要讀歷史資料時，不需要知道「這份資料是下載器下載的」還是「手動放進去的」——只要知道 `<base_dir>/<SYMBOL>/<interval>/<SYMBOL>-<interval>-<year>-<month>.csv` 這個路徑規則（`at_downloader::local_path` 就是算這個路徑的函式），呼叫 `at_core::read_bars_file` 直接讀回 `Vec<Bar>` 就好。要下載一段連續的歷史（例如 2023 年全年），呼叫端目前需要自己迴圈呼叫 `download_and_store_monthly_klines` 12 次（每次一個月）；如果之後發現這個迴圈邏輯值得抽出來（例如要處理「某個月還沒有資料、要重試或跳過」的情況），再回來加一個「下載一段日期範圍」的函式，現在只做「下載指定一個月」這個最小單位就夠。
