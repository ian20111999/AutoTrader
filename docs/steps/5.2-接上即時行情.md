# 5.2 接上即時行情：收盤的 K 線才進帳本

把 4.5 的 WebSocket 行情接上 5.1 的 `PaperEngine`：即時收到一根**已收盤**的 K 線 → 餵給引擎 →
引擎算出新的權益點 → 往外送給消費端（5.4 的畫面就是消費端）。

這一步沒有任何送出訂單的程式碼路徑：新 crate 只依賴 `at-core`（算帳）與 `at-market-stream`
（讀公開行情），完全沒有 `at-binance`，也不讀 Keychain。

## 做了什麼

新開一個 crate：`crates/paper-trading`（package 名 `at-paper-trading`），只有一個檔案
`src/lib.rs`，大約 60 行程式 + 測試。

對外的公開介面：

```rust
pub fn spawn(
    stream: MarketStreamHandle,          // 4.5 的行情控制代碼，整個搬進背景執行緒
    strategy: Box<dyn Strategy + Send>,  // 2.1 的策略介面
    config: &BacktestConfig,             // 2.2-2.5 的成本／槓桿設定
) -> Result<PaperTradingHandle, BacktestError>;

pub struct PaperTradingHandle {
    pub updates: std::sync::mpsc::Receiver<PaperUpdate>,
    // ...
}

pub enum PaperUpdate {
    /// 一根收盤 K 線進帳本之後的最新狀態。
    Bar(PaperSnapshot),
    /// 引擎算不下去了：帳本從這一刻起不完整，這條串流到此結束。
    Failed(BacktestError),
}

pub struct PaperSnapshot {
    pub point: EquityPoint,   // 這根收盤時的時間 + 帳戶總值
    pub cash: Fixed,          // 報價幣現金（負數＝有槓桿）
    pub position: Fixed,      // 帶正負號的持倉數量（正多、負空、0 空手）
    pub trades: usize,        // 到目前為止的成交筆數（爆倉也算一筆）
    pub liquidations: usize,  // 到目前為止的強制平倉次數
}
```

用起來像這樣：

```rust
let stream = at_market_stream::spawn(at_market_stream::kline_stream("BTCUSDT", Interval::M1));
let paper = at_paper_trading::spawn(stream, Box::new(strategy), &config)?;

for update in paper.updates {
    match update {
        PaperUpdate::Bar(s) => println!("{} 權益 {} 部位 {}", s.point.open_time, s.point.equity, s.position),
        PaperUpdate::Failed(e) => { eprintln!("模擬交易中止：{e}"); break; }
    }
}
```

核心迴圈（私有的 `run`）只有一件事，跑在自己的背景執行緒上：

```
收 MarketEvent → 是 Kline 嗎？→ is_closed 嗎？→ engine.on_bar(bar, strategy)
                      ↓ 不是          ↓ 還沒收盤          ↓ Ok → 送 PaperUpdate::Bar
                     路過            路過                ↓ Err → 送一次 Failed，然後停止
```

## 為什麼多開一個 crate

這一步要同時用到 `at-core`（引擎、策略、`Bar`）和 `at-market-stream`（WebSocket），但這兩個
crate 都不該依賴對方：

- `at-core` 目前是**零外部依賴**的地基，回測、模擬、測試網、實盤共用。把 WebSocket／TLS／JSON
  拖進去，等於以後每次編譯純算帳的程式都要連 `tungstenite` 一起編，而且「算帳」從此和「怎麼拿到
  資料」綁死。
- 反過來讓 `at-market-stream` 依賴引擎，會變成「收行情的人自己決定要不要記帳」，職責也是錯的。

所以接線邏輯住在第三個很小的 crate 裡，`at-core` 和 `at-market-stream` 都維持原樣（這一步只
在 `crates/core/src/lib.rs` 的 `pub use` 補上 `PaperEngine` 這一個名字，5.1 刻意留到現在才加）。
這和 4.3／4.4 的做法一致：`at-account-sync` 也是為了接 `at-binance` 和 `at-core` 才存在的。

## 為什麼只有 `is_closed == true` 才餵

Binance 的 kline 串流每秒左右就推一則「這根還在形成中」的訊息，`open_time` 都一樣、收盤價一直在
變（4.5 已經查證過這個陷阱）。如果照收照餵：

1. 策略的契約會被打破（2.1：「同一根只餵一次、按時間遞增」）。同一根 K 線會被問幾十次，收盤價
   每次都不同，訊號在一分鐘內閃爍好幾回，然後下一根開盤按最後一次的答案成交——這不是策略的行為。
2. 5.1 的引擎會用 `open_time` 檢查時間遞增，同一根餵第二次會直接回 `NonMonotonicTime`。

所以過濾這件事必須發生在餵之前，而且要有測試把它釘住（見下面第一條測試）。ticker 事件同理路過：
它連 K 線都不是。

## 引擎回錯誤就停

`on_bar` 回 `Err` 之後，帳本已經不完整（可能是資金費收了一半、可能是成交算到溢位）。這時候繼續
餵下一根，畫面上會出現一條「看起來很正常、其實是假的」權益曲線——這比直接停掉危險得多。

所以錯誤的處理是：往外送**一次** `PaperUpdate::Failed(error)`，然後結束背景執行緒。消費端收到
它就知道「從這根開始的數字不可信，該停止並告訴使用者」。之後不會再有任何更新。

## 怎麼驗證

```bash
# 1. 三道關卡
cargo fmt --all
cargo clippy --all-targets -- -D warnings
cargo test

# 2. 只看這一步新增的測試（應該是 4 passed + 1 ignored）
cargo test -p at-paper-trading

# 3. 真的連 Binance 跑一遍（需要網路，最多要等一根 1 分鐘 K 線收盤）
cargo test -p at-paper-trading -- --ignored --nocapture
```

第 3 條在實機上的輸出（2026-09-30，等了 40.86 秒）：

```
收到真實收盤 K 線的模擬交易更新：時間 1790753220000、權益 10000、現金 10000、部位 0
test tests::runs_against_the_real_binance_kline_stream ... ok
```

四個自動測試各自釘住一件事：

| 測試 | 釘住什麼 |
|---|---|
| `only_closed_klines_are_fed_to_the_engine` | 餵 7 則事件（未收盤 K 線 ×3、ticker ×2、收盤 ×2），策略只能被問到那 2 根——用假策略記下的呼叫次數與 `open_time` 序列判斷，不是看權益數字（這裡策略全程空手，權益不受成交價影響，換成任何一根未收盤的價格斷言都不會變；真正抓漏放的機制是：兩根未收盤 K 線跟同一根收盤 K 線的 `open_time` 相同，如果漏放進去會連續餵到兩個相同時間戳，觸發 `NonMonotonicTime` 讓假策略只被問到 1 次而不是 2 次） |
| `a_stream_with_no_closed_klines_produces_no_updates` | 一根都還沒收盤時，策略完全不會被問、也不送任何更新 |
| `engine_error_is_reported_once_and_stops_the_feed` | 第二根 K 線跟第一根 `open_time` 相同（用 `<=` 判斷，不是嚴格倒退）→ 送一則 `Failed(NonMonotonicTime { index: 1 })` 就停，**後面那根時間正常的 K 線也不再餵** |
| `same_bars_give_the_same_numbers_as_a_backtest` | 同樣 5 根 K 線走「即時管線」和走 `run_backtest`，權益曲線逐點相等、成交筆數與爆倉次數相同 |

測試怎麼做到不連網路：`run` 收的是一個普通的 `mpsc::Receiver<MarketEvent>`，測試直接塞假事件
進去、關掉發送端，然後在**當前執行緒**呼叫 `run`（它收到 channel 關閉就會自然結束）。
「引擎真的餵了哪幾根」的證據不是看回傳值，而是用一個會把 `bar.open_time` 記下來的假策略——
因為 `on_bar` 每餵一根就一定會問策略一次。

## 建議閱讀順序

1. `crates/paper-trading/src/lib.rs` 開頭的模組說明（為什麼獨立成 crate、為什麼只餵收盤的）。
2. 同檔的 `run`：整個資料管線就這二十幾行，三個出口都在文件註解裡寫清楚了。
3. `spawn`：設定不合法時**當場**回錯誤（不會開執行緒），因為 `PaperEngine::new` 先跑。
4. 測試裡的 `feed` 輔助函式：假 channel 怎麼取代真 WebSocket。
5. 回頭看 `crates/core/src/backtest.rs` 的 `PaperEngine::on_bar`——這一步完全沒有改它，
   即時交易和回測跑的是同一段程式。

## 動手試試看

1. 把 `run` 裡的 `if !update.is_closed { continue; }` 註解掉，跑
   `cargo test -p at-paper-trading`。`only_closed_klines_are_fed_to_the_engine` 會失敗，而且
   你會看到引擎開始回 `NonMonotonicTime`——這就是「未收盤的 K 線不能餵」的具體後果。
2. 把錯誤分支的 `return` 改成 `continue`，跑同一組測試。
   `engine_error_is_reported_once_and_stops_the_feed` 會失敗：策略多看到一根，帳本已經不完整
   卻還在產生新的權益點。
3. 在 `same_bars_give_the_same_numbers_as_a_backtest` 裡把策略換成 `TargetPosition::short(...)`
   或加上手續費（`BacktestConfig` 的 `fees`／`slippage`），確認即時管線和回測還是逐點相等。

## 還沒做的事

- **沒有停止開關。** 現在要停只能把 `PaperTradingHandle` drop 掉，背景執行緒會在下一次送出更新
  時才發現沒人收（和 4.5 的行情執行緒同一個模式）。使用者按「停止」要立刻生效是 5.3 的事。
- **未收盤的 K 線與 ticker 目前直接丟掉，沒有往外送。** 5.4 的畫面想顯示即時跳動的價格時，
  要嘛在這裡多加一種 `PaperUpdate`，要嘛自己再訂一條 ticker 串流。等畫面真的要用再決定，
  現在多送只是多一種沒人看的事件。
- **斷線期間漏掉的 K 線不會補。** 4.5 斷線後會自動重連，但重連空窗期收盤的 K 線就是沒收到，
  引擎也就不知道有這一根（權益曲線會缺一點）。要補的話得用 REST 把缺口抓回來，屬於 5.3 之後
  的可靠性議題。
- **只吃一條串流、一個交易對。** 多商品同時模擬要到更後面才處理。
