# 6.3 風控層：下單前的檢查閘門

新 crate `at-risk-control`，在 6.4 把策略接上測試網下單之前，先把「要不要讓這筆單送出去」
的政策獨立出來，用正常情境＋邊界情境的測試先行驗證過，再讓 6.4 依賴它。

## 做了什麼

- `RiskLimits`：每日虧損上限、單筆下單金額上限，只能用 `RiskLimits::new` 建立（兩個上限都
  強制大於 0），拿到手上的一定是檢查過的設定。
- `RiskLimits::check(&AccountState, &ProposedOrder) -> Result<(), Blocked>`：下單前的唯一
  入口。檢查順序（最絕對的先講）：
  1. 一鍵停止（`kill_switch`）—— 連平倉單都擋，沒有例外。
  2. 下單數量／參考價必須是正數。
  3. 今日損益必須算得出來（`daily_pnl: Option<Fixed>` 是 `None` 就直接擋，不當成 0）。
  4. 今日損益達到虧損上限時，只擋「會增加曝險」的單；降低曝險（平倉／減碼／多翻空再反向
     收斂）的單放行。
  5. 單筆下單金額（數量 × 參考價）超過上限就擋。
- `DailyPnl`：按 UTC 日界（`ms.div_euclid(86_400_000)`）自動歸零，`update(now_ms, equity)`
  只在新的一天才重新設定基準權益，回傳當日損益；時鐘往回跳不會誤觸重置。
- 所有算術用 `checked_add`/`checked_sub`/`checked_mul`，任何溢位都轉成 `Blocked::Overflow`
  擋下這筆單，不會 panic。

## 為什麼這樣設計

### 一鍵停止連平倉都擋

一鍵停止存在的理由就是「不再相信這套自動化」——策略寫錯、迴圈失控、餵錯交易對。如果它放行
「降低風險的單」，閘門就必須相信下單方自己對「這是平倉」的分類；而一個會把加碼誤判成平倉的
程式，剛好就是最需要按下停止鍵的那個程式。選的失效模式是「按下去之後一張單都不送」，既有
部位請用交易所自己的 App 手動處理，不依賴這份程式碼正確。

### 虧損上限只擋增加曝險的單，不自動強制平倉

虧到上限時要做的是「停止繼續虧更多」，把部位往 0 收的單必須放行，否則使用者會被鎖在部位
裡出不來。自動強制平倉本身是另一個有風險的自動化動作（市價砸出去可能剛好砸在最差的價格），
這一步不做，交給使用者按一鍵停止後手動處理。「降低曝險」的判斷不接受下單方自己貼標籤——
用送單前後的部位正負號、是否過零來判斷，過零（多翻空／空翻多）一律當成增加曝險，不管過零後
金額有沒有變小。

### 判不出來就擋（fail closed）

今日損益算不出來、金額溢位、數量或價格不是正數——任何閘門自己也不確定的情況都回 `Err`。
放行一筆看不懂的單，比擋下一筆合法的單後果嚴重得多。

### 獨立成一個 crate

這一層是「要不要送單」的政策，不是回測引擎共用的地基型別，不該讓零外部依賴的 `at-core`
背著一份帳戶層的風控設定。獨立出來還有個好處：6.4 的下單路徑在 `Cargo.toml` 上就看得出來
一定依賴 `at-risk-control`，少一條繞過閘門的暗路。

## 跨模型審查

Codex 對這份實作做過一次對抗式審查（鎖定邏輯正確性、fail-closed 行為、溢位/panic
安全），確認兩個政策決定（一鍵停止連平倉也擋；虧損上限只擋增加曝險的單）都站得住腳，沒有
發現真的 bug。

## 怎麼驗證

```bash
cargo fmt --all
cargo clippy --all-targets -- -D warnings
cargo test -p at-risk-control
```

全部通過，涵蓋一鍵停止、數量/價格非正數、損益未知、虧損達標但平倉放行、虧損達標且加碼擋下、
單筆金額超限、跨日歸零、時鐘倒退不誤觸重置、溢位安全等情境。

## 建議閱讀順序

1. `crates/risk-control/src/lib.rs` 開頭的模組說明，理解兩個設計決定的理由。
2. `RiskLimits::check`：唯一的檢查入口，順序就是程式碼本身的順序。
3. `DailyPnl::update`：跨日歸零怎麼用純函式/純方法做到不碰系統時鐘。

## 動手試試看

1. 把 `check` 裡 `pnl <= loss_floor` 的 `<=` 改成 `<`，重跑測試，看哪個測試會失敗——確認
   「剛好打到虧損上限」這個邊界現在是擋下的。
2. 想一個你覺得風控閘門「應該擋但現在沒擋」的情境，寫一個新測試看它過不過，再決定要不要
   回報調整。
